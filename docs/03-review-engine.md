## 1. 审查请求完整生命周期

审查请求从用户提交到最终返回结果，经历 **6 个阶段**的流水线处理。每个阶段职责明确、可独立监控、可单独扩缩容。

```
                        ┌─────────────────────────────┐
                        │  用户上传审查请求              │
                        │  • 上传文件/粘贴文本           │
                        │  • 选择产品类型(可选)          │
                        │  • 选择内容类型(可选, 可自动识别)│
                        │  • 选择渠道(可选)              │
                        └──────────┬──────────────────┘
                                   │
                    ┌──────────────┼──────────────────┐
                    │              │                    │
                    ▼              ▼                    ▼
              ┌──────────┐  ┌──────────┐         ┌──────────┐
    阶段1     │ 快速过滤  │  │ 格式校验  │         │ 任务创建  │
              │ (禁用词   │  │ (大小/   │         │ (审查ID  │
              │  黑名单)  │  │  类型)   │         │  生成)   │
              └─────┬────┘  └─────┬────┘         └─────┬────┘
                    │              │                    │
                    └──────────────┼────────────────────┘
                                   │
                                   ▼
              ┌─────────────────────────────────────────────┐
    阶段2     │  内容解析                                    │
              │                                             │
              │  图片 → OCR + 布局分析                       │
              │  PDF  → 文档解析 + 章节拆分                  │
              │  文本 → 直接分段                             │
              │  视频 → 关键帧提取 + OCR + 语音转文字         │
              │                                             │
              │  输出: 分段的纯文本 + 元数据                  │
              └──────────────────────┬──────────────────────┘
                                     │
                                     ▼
              ┌─────────────────────────────────────────────┐
    阶段3     │  ACE 上下文动态组装 (核心)                    │
              │                                             │
              │  A. 按内容类型检索 → 该类型的格式/完整性要求   │
              │  B. 按产品类型检索 → 该产品的特定法规          │
              │  C. 按内容语义检索 → 各段文字匹配的法条        │
              │  D. 按内容语义检索 → 相似历史案例              │
              │  E. 加载企业自定义规则                        │
              │                                             │
              │  合并去重 → 上下文 token 预算控制 → 最终上下文 │
              └──────────────────────┬──────────────────────┘
                                     │
                                     ▼
              ┌─────────────────────────────────────────────┐
    阶段4     │  Prompt 组装 + LLM 调用                      │
              │                                             │
              │  System Prompt + 法规上下文 + 案例上下文       │
              │  + 企业规则 + 审查指令 + 待审查内容            │
              │                                             │
              │  → 调用 LLM                                  │
              │  → 解析结构化 JSON 输出                       │
              └──────────────────────┬──────────────────────┘
                                     │
                                     ▼
              ┌─────────────────────────────────────────────┐
    阶段5     │  结果后处理                                   │
              │                                             │
              │  • 法条引用校验 (防幻觉)                      │
              │  • 审查结果结构化                             │
              │  • 风险评分计算                               │
              │  • 审查报告生成                               │
              └──────────────────────┬──────────────────────┘
                                     │
                                     ▼
              ┌─────────────────────────────────────────────┐
    阶段6     │  返回结果 + 进入人工复核队列                   │
              └─────────────────────────────────────────────┘
```

### 各阶段关键说明

| 阶段 | 核心职责 | 耗时预算 | 失败处理 |
|------|----------|----------|----------|
| 阶段1: 快速过滤 | 禁用词匹配 (Aho-Corasick)、格式校验、任务ID生成 | < 10ms | 格式不合法直接拒绝；禁用词命中标记但继续流程 |
| 阶段2: 内容解析 | OCR、文档解析、分段 | 500ms - 3s | OCR 失败降级为纯文本；解析异常进入人工队列 |
| 阶段3: ACE 上下文组装 | 五路并行检索 + 合并去重 + token 预算控制 | 200ms - 500ms | 单路检索超时不阻塞整体；至少保证向量检索可用 |
| 阶段4: LLM 调用 | Prompt 组装 + 模型推理 + 结构化输出解析 | 3s - 15s | JSON 解析失败重试；主模型不可用切备用模型 |
| 阶段5: 后处理 | 法条引用校验 + 风险评分 + 报告生成 | 100ms | 校验失败不阻塞，标记为 unverified |
| 阶段6: 返回结果 | 结果持久化 + 推送通知 + 进入复核队列 | 50ms | 持久化失败重试 |

## 2. LLM 调用方式详解 — 审查层

### 2.1 调用方式：Spring AI ChatClient 直接 API 调用

审查层的 LLM 调用采用 **Spring AI ChatClient 直接调用外部模型 API** 的方式，而非微调（fine-tuning）或本地部署模型。

核心原因：
- **法规知识通过 RAG 检索注入上下文**，不需要将法规"训练"进模型权重
- **合规标准频繁更新**（新法规发布、旧法规废止），微调模型无法及时跟进
- **可审计性要求**：每次审查的依据必须明确来自检索到的法条，而非模型"记住"的知识
- **多模型灵活切换**：不同租户可配置不同模型，主备模型可无缝切换

### 2.2 模型选型：快速 + 高质量

审查层是在线服务，**延迟直接影响用户体验**。模型选型策略：

| 优先级 | 模型 | 特点 | 适用场景 |
|--------|------|------|----------|
| 主模型 | GPT-4o | 速度快、指令遵从强、JSON 输出稳定 | 日常审查 |
| 备用模型1 | Claude 3.5 Sonnet | 长上下文能力强、推理质量高 | 长文档审查、主模型不可用时 |
| 备用模型2 | 通义千问-Max / DeepSeek | 中文理解优秀、国内部署延迟低 | 国内部署场景、成本敏感场景 |

> **注意**：知识构建层（离线法条解析）可以使用更慢但更强的模型（如 Claude 3 Opus），因为离线处理不受延迟约束。审查层必须使用快速模型。

### 2.3 结构化输出：BeanOutputConverter 强制 JSON Schema

审查结果必须是严格的结构化 JSON，不能依赖 LLM "自觉"输出正确格式。Spring AI 提供 `BeanOutputConverter` 机制：

```
工作原理:

1. 定义 Java Record/Class → ReviewResult
2. BeanOutputConverter 自动从 Java 类型生成 JSON Schema
3. JSON Schema 注入到 System Prompt 的末尾
4. LLM 输出 JSON → Spring AI 自动反序列化为 Java 对象
5. 如果反序列化失败 → 触发重试逻辑
```

### 2.4 Prompt 工程：三段式 Prompt 组装

完整 Prompt 由三部分组成：

```
┌──────────────────────────────────────────────────────────────┐
│  System Prompt (系统指令)                                      │
│                                                              │
│  • 角色设定：资深金融合规审查专家                                │
│  • 审查要求：必须基于提供的法规和案例、不得编造法条               │
│  • 检索到的法规上下文 (ACE 组装结果)                            │
│  • 检索到的案例上下文 (ACE 组装结果)                            │
│  • 企业自定义规则                                              │
│  • JSON 输出格式约束 (BeanOutputConverter 自动生成)             │
│  ~10,000 tokens                                               │
├──────────────────────────────────────────────────────────────┤
│  User Prompt (用户内容)                                        │
│                                                              │
│  • 内容元数据 (内容类型、产品类型、渠道)                         │
│  • 分段后的待审查内容                                          │
│  ~2,000 tokens                                                │
├──────────────────────────────────────────────────────────────┤
│  预留输出空间                                                  │
│  ~3,000 tokens                                                │
└──────────────────────────────────────────────────────────────┘
  总计: ~15,000 tokens
```

### 2.5 关键参数配置

| 参数 | 设定值 | 理由 |
|------|--------|------|
| Temperature | **0 或 0.1** | 合规审查需要确定性输出，不需要创造性。相同内容两次审查应给出一致结论 |
| Max Tokens | **动态计算** | `max_tokens = max(2000, content_length * 3)`，确保输出空间足够但不浪费 |
| Top-P | 1.0 | 配合低 temperature 使用 |
| Response Format | JSON | 强制 JSON 输出模式（如模型支持） |

### 2.6 伪代码示例

```java
// Pseudocode for review LLM call
ChatClient chatClient = ChatClient.builder(openAiModel)
    .defaultSystem(systemPrompt)
    .build();

ReviewResult result = chatClient.prompt()
    .user(assembledUserPrompt)  // includes content + context
    .call()
    .entity(ReviewResult.class);  // Spring AI auto-parses JSON to Java object
```

实际调用链路的完整伪代码：

```java
// 1. 构建 ChatClient（应用启动时初始化，非每次请求创建）
ChatClient chatClient = ChatClient.builder(chatModel)
    .defaultSystem(reviewSystemPrompt)
    .defaultOptions(ChatOptionsBuilder.builder()
        .withTemperature(0.0)
        .build())
    .build();

// 2. 组装用户 Prompt（ACE 上下文已注入 System Prompt）
String userPrompt = String.format(
    "请审查以下%s内容（%s，%s渠道）：\n\n%s",
    contentType, productType, channel, segmentedContent
);

// 3. 动态计算 maxTokens
int maxTokens = Math.max(2000, segmentedContent.length() * 3);

// 4. 调用 LLM 并自动解析为结构化对象
ReviewResult result = chatClient.prompt()
    .user(userPrompt)
    .options(ChatOptionsBuilder.builder()
        .withMaxTokens(maxTokens)
        .build())
    .call()
    .entity(ReviewResult.class);
```

### 2.7 重试与容错策略

```
LLM 调用
    │
    ├─ 成功 → JSON 解析
    │           │
    │           ├─ 解析成功 → 返回 ReviewResult ✅
    │           │
    │           └─ 解析失败 → 重试 (附带纠正 Prompt)
    │                          │
    │                          │  纠正 Prompt:
    │                          │  "你的上次输出不是合法JSON，请重新输出。
    │                          │   严格遵循以下 JSON Schema: {schema}"
    │                          │
    │                          ├─ 重试1 → 解析成功 → 返回 ✅
    │                          ├─ 重试2 → 解析成功 → 返回 ✅
    │                          └─ 重试3 → 仍失败 → 切换备用模型
    │
    └─ 调用失败 (超时/API错误)
                │
                ├─ 重试1 (指数退避 1s)
                ├─ 重试2 (指数退避 2s)
                └─ 重试3 → 仍失败 → 切换备用模型
                                      │
                                      ├─ 备用模型成功 → 返回 ✅
                                      └─ 备用模型也失败 → 进入人工队列 ⚠️
```

**Fallback 策略**：如果主模型（如 GPT-4o）连续 3 次调用失败（包括 JSON 解析失败），自动切换到备用模型（如 Claude 3.5 Sonnet）。切换后标记审查结果的 `llm_model` 字段为实际使用的模型，便于后续质量分析。

### 2.8 流式输出：长内容场景

对于长文档审查（内容超过 5000 字），LLM 推理时间可能超过 10 秒。为降低用户感知延迟，使用 **流式输出 (Streaming)**：

```
非流式:  用户等待 ████████████████ 15s 后一次性返回结果
流式:    用户看到 █ 1s 首字节 → 逐步填充结果 → 15s 完成

流式实现:
chatClient.prompt()
    .user(userPrompt)
    .stream()
    .content()         // 返回 Flux<String>，逐 token 推送
    .collectToString() // 最终收集完整 JSON 后解析
```

前端展示策略：
- 流式接收过程中，前端显示"正在审查中..."动画
- 当完整 JSON 接收完毕后，一次性渲染审查结果
- 如果需要实时展示审查进度，可以在 LLM 输出中约定 `segments` 数组逐个输出，前端逐段渲染

## 3. ACE 上下文组装 — 核心细节

### 3.1 五路检索策略

ACE（Agentic Context Engineering）的核心思想：**不维护静态的"内容类型→规则集"映射，而是每次审查时根据内容动态检索最相关的法规、案例和规则，组装为 LLM 的上下文。**

```
┌─────────────────────────────────────────────────────────────────────┐
│  ACE 上下文组装器 (ContextAssembler)                                 │
│                                                                     │
│  输入:                                                               │
│  • 解析后的内容段落列表: List<ContentSegment>                         │
│  • 内容元数据: ContentMeta (content_type, product_type, channel)     │
│  • 租户配置: TenantConfig                                           │
│                                                                     │
│  ┌───────────────────────────────────────────────────────────────┐  │
│  │  检索路径 A: 按内容类型 (结构化查询)                            │  │
│  │                                                               │  │
│  │  SELECT * FROM law_knowledge                                  │  │
│  │  WHERE 'content_type' IN applicable_content_types             │  │
│  │  AND status = 'published'                                     │  │
│  │                                                               │  │
│  │  content_type = "营销海报"                                     │  │
│  │  → 命中: 海报格式要求、字号要求、必备元素、风险提示位置要求等    │  │
│  │  → 预期结果: ~15 条法条知识                                    │  │
│  └───────────────────────────────────────────────────────────────┘  │
│                                                                     │
│  ┌───────────────────────────────────────────────────────────────┐  │
│  │  检索路径 B: 按产品类型 (结构化查询)                            │  │
│  │                                                               │  │
│  │  SELECT * FROM law_knowledge                                  │  │
│  │  WHERE 'product_type' IN applicable_product_types             │  │
│  │  AND status = 'published'                                     │  │
│  │                                                               │  │
│  │  product_type = "公募基金"                                     │  │
│  │  → 命中: 公募基金销售规范、信息披露要求、适当性要求等            │  │
│  │  → 预期结果: ~20 条法条知识                                    │  │
│  └───────────────────────────────────────────────────────────────┘  │
│                                                                     │
│  ┌───────────────────────────────────────────────────────────────┐  │
│  │  检索路径 C: 按内容语义 (向量检索 — 最关键)                     │  │
│  │                                                               │  │
│  │  对每个内容段落:                                               │  │
│  │    segment_embedding = embed(segment.text)                    │  │
│  │    results = milvus.search(                                   │  │
│  │      collection = "law_knowledge_vectors",                    │  │
│  │      vector = segment_embedding,                              │  │
│  │      top_k = 10,                                              │  │
│  │      filter = "status == 'published'"                         │  │
│  │    )                                                          │  │
│  │                                                               │  │
│  │  示例:                                                         │  │
│  │  "过去一年涨幅达35%" → 匹配到:                                 │  │
│  │    - 第24条: 不得以预期收益率宣传 (相似度: 0.87)                │  │
│  │    - 第25条: 展示业绩需标注时间区间 (相似度: 0.84)              │  │
│  │                                                               │  │
│  │  "亏损概率很小" → 匹配到:                                      │  │
│  │    - 第24条第2项: 不得以保本方式宣传 (相似度: 0.91)             │  │
│  │                                                               │  │
│  │  → 预期结果: ~25 条法条知识(去重后)                             │  │
│  └───────────────────────────────────────────────────────────────┘  │
│                                                                     │
│  ┌───────────────────────────────────────────────────────────────┐  │
│  │  检索路径 D: 相似历史案例 (向量检索)                            │  │
│  │                                                               │  │
│  │  对每个内容段落:                                               │  │
│  │    results = milvus.search(                                   │  │
│  │      collection = "review_cases_vectors",                     │  │
│  │      vector = segment_embedding,                              │  │
│  │      top_k = 3,                                               │  │
│  │      filter = "verdict IN ['violation', 'compliant']          │  │
│  │               AND human_confirmed = true"                     │  │
│  │    )                                                          │  │
│  │                                                               │  │
│  │  仅检索人工已确认的案例，确保案例质量                            │  │
│  │  → 预期结果: ~10 条相似案例                                    │  │
│  └───────────────────────────────────────────────────────────────┘  │
│                                                                     │
│  ┌───────────────────────────────────────────────────────────────┐  │
│  │  检索路径 E: 企业自定义规则 (直接加载)                          │  │
│  │                                                               │  │
│  │  SELECT * FROM tenant_custom_rules                            │  │
│  │  WHERE tenant_id = :current_tenant                            │  │
│  │  AND enabled = true                                           │  │
│  │                                                               │  │
│  │  → 预期结果: ~5-20 条企业规则                                  │  │
│  └───────────────────────────────────────────────────────────────┘  │
│                                                                     │
│  ┌───────────────────────────────────────────────────────────────┐  │
│  │  合并与去重                                                    │  │
│  │                                                               │  │
│  │  所有检索结果按 article_id 去重                                │  │
│  │  按相关度得分排序                                              │  │
│  │  Token 预算控制:                                               │  │
│  │    • System Prompt: ~500 tokens                               │  │
│  │    • 法规上下文: 最多 ~6000 tokens (~50 条法条摘要)             │  │
│  │    • 案例上下文: 最多 ~3000 tokens (~10 条案例摘要)             │  │
│  │    • 企业规则: 最多 ~1000 tokens                               │  │
│  │    • 待审查内容: ~2000 tokens                                  │  │
│  │    • 输出预留: ~3000 tokens                                    │  │
│  │    • 总计: ~15,500 tokens (适配大部分 LLM 上下文窗口)           │  │
│  │                                                               │  │
│  │  如果超出预算:                                                 │  │
│  │    按相关度得分从低到高裁剪法条和案例                            │  │
│  └───────────────────────────────────────────────────────────────┘  │
└─────────────────────────────────────────────────────────────────────┘
```

### 3.2 混合检索策略 — 为什么单纯向量检索不够

在合规审查场景中，**纯向量语义检索存在固有局限性**。本系统采用四种检索手段互补的混合检索架构，确保法条检索的准确率和召回率同时达标。

#### 3.2.1 四种检索手段

**① 向量语义检索 (Milvus)**

向量检索的核心优势在于**语义理解**——它能捕捉到文字表面不同但含义相近的匹配。

| 待审查内容 | 命中法条 | 匹配原理 |
|-----------|---------|---------|
| "亏损概率很小" | 第24条第2项：不得以保本方式宣传 | "亏损概率很小"的语义接近"保本承诺"，虽然没有直接说"保本" |
| "买入后躺赚" | 第24条第1项：不得以预期收益宣传 | "躺赚"的语义隐含"确定性收益"，向量空间中与"预期收益"相近 |

但纯向量检索存在以下问题：
- **关键词盲区**：如果待审内容中出现"预期收益率"这个精确关键词，向量检索可能把它排在第3-5位，而不是第1位——因为向量空间中语义相近的结果很多
- **结构化字段无法利用**：向量检索无法做"只查公募基金相关法条"这种精确过滤（虽然 Milvus 支持 filter，但这本质上是向量+过滤的组合，不是独立检索路径）
- **同义词缺失**：某些行业术语的同义词关系，Embedding 模型不一定充分学习到

**② 结构化字段查询 (PostgreSQL)**

结构化查询的核心优势在于**确定性**——精确匹配内容类型和产品类型字段，零误差。

```sql
-- 当用户上传一张"营销海报"审查"公募基金"产品时
SELECT * FROM law_articles
WHERE '营销海报' = ANY(applicable_content_types)
  AND '公募基金' = ANY(applicable_product_types)
  AND status = 'published';
```

这种查询是**确定性的，不是概率性的**。只要知识构建阶段正确标注了法条的 `applicable_content_types` 和 `applicable_product_types`，就一定能命中。

典型场景：
- 用户上传"营销海报" → 直接命中海报格式要求、字号要求、必备元素规定
- 用户选择"公募基金" → 直接命中公募基金销售管理办法所有相关条款

**③ 关键词/BM25 检索 (Elasticsearch)**

关键词检索的核心优势在于**精确关键词匹配**——当内容中出现法规原文中的精确术语时，BM25 能直接命中。

| 待审查内容 | ES 命中 | 匹配原理 |
|-----------|---------|---------|
| "预期收益率20%" | 法条 key_phrases 包含"预期收益率" | 精确关键词匹配，BM25 得分极高 |
| "基金业绩排名" | 法条 key_phrases 包含"基金业绩"、"排名" | 多关键词同时命中，TF-IDF 加权 |
| "保本保收益" | 法条 original_text 包含"保本、保收益" | 直接匹配法条原文 |

关键词检索与向量检索互补：
- 向量检索擅长**语义模糊匹配**（"躺赚" → "预期收益"）
- 关键词检索擅长**术语精确匹配**（"预期收益率" → "预期收益率"）

**④ 知识图谱查询 (Neo4j)**

知识图谱的核心优势在于**关系推理**——通过实体之间的关系链路发现间接关联的法条。

```cypher
// 审查"公募基金"产品时，通过 APPLIES_TO 关系找到所有适用法条
MATCH (a:Article)-[:APPLIES_TO]->(p:ProductType {name: '公募基金'})
RETURN a

// 进一步：通过法条间的交叉引用，找到关联法条
MATCH (a:Article)-[:APPLIES_TO]->(p:ProductType {name: '公募基金'})
MATCH (a)-[:REFERENCES]->(related:Article)
RETURN a, related
```

图谱检索的独特价值：
- **关联发现**：第24条引用了广告法第4条 → 图谱自动把广告法相关条款也纳入上下文
- **替代关系**：旧法条被新法条 SUPERSEDED_BY → 图谱确保使用最新法条
- **主体约束**：某法条只约束"基金销售机构" → 图谱可以根据审查主体过滤不适用的法条

#### 3.2.2 Reciprocal Rank Fusion (RRF) 融合算法

四路检索的结果通过 **RRF（倒数排名融合）** 算法合并为统一的排序：

```
score_final = Σ 1/(k + rank_i) for each retrieval path i
```

其中 `k` 通常取 **60**。RRF 的核心思想：**如果一条法条在多个检索路径中都排名靠前，那它更可能是真正相关的。**

计算示例：

```
法条: 第24条第1款第1项 "不得以预期收益率宣传"

  向量检索排名:  rank = 2   → 1/(60+2)  = 0.01613
  关键词检索排名: rank = 1   → 1/(60+1)  = 0.01639
  结构化查询:    rank = 5   → 1/(60+5)  = 0.01538
  图谱查询:      rank = 3   → 1/(60+3)  = 0.01587
  ─────────────────────────────────────────────
  RRF 总分:                   = 0.06377 (高分，多路交叉验证)

法条: 广告法第9条 "不得使用极限词"

  向量检索排名:  rank = 8   → 1/(60+8)  = 0.01471
  关键词检索排名: 未命中      → 0
  结构化查询:    未命中      → 0
  图谱查询:      rank = 12  → 1/(60+12) = 0.01389
  ─────────────────────────────────────────────
  RRF 总分:                   = 0.02860 (较低，只有两路命中)
```

#### 3.2.3 为什么混合检索比纯向量检索更准确

以具体例子说明：

**场景**: 待审查内容包含 "收益率20%"

| 检索路径 | 命中内容 | 匹配方式 |
|---------|---------|---------|
| 关键词检索 (ES) | key_phrases 包含"预期收益率" → **精确匹配** | "收益率"是"预期收益率"的子串，BM25 高分命中 |
| 向量检索 (Milvus) | violation_examples 包含"预期年化收益12%" → **语义匹配** | "收益率20%"与"年化收益12%"在向量空间语义接近 |
| 结构化查询 (PG) | 如果已知是"营销海报"类型 → **确定性命中** | 精确匹配 applicable_content_types |
| 图谱查询 (Neo4j) | 第24条关联的所有法条 → **关系推理** | 通过 REFERENCES 边发现关联条款 |

**两种信号通过 RRF 互相增强**：
- 关键词检索确保"预期收益率"这个精确术语不被遗漏
- 向量检索确保语义相近但措辞不同的法条也被召回
- 结构化查询确保该内容类型/产品类型的基础法规一定在上下文中
- 图谱查询确保法条间的关联关系不被忽略

**如果只用纯向量检索**：
- "收益率20%"的向量可能与很多包含"收益"的法条都有中等相似度
- 真正精确匹配"预期收益率"的法条可能被排到第 5-8 位
- 而混合检索中，关键词检索将其直接推到第 1 位，RRF 融合后该法条排名大幅提升

{tenant_custom_rules}

### 5.3 风险评分机制 — 两级评分体系

风险评分是**两级的**，从审查点级别汇总到任务级别：

#### 第一级：审查点级别

每个 `issue` 有自己的 `severity`，对应一个固定分值：

| severity | 分值 | 含义 | 示例 |
|----------|------|------|------|
| `critical` | +30 | 严重违规，可能导致行政处罚 | 保本承诺、虚假宣传 |
| `major` | +20 | 重要违规，违反明确法条 | 业绩数据缺失来源和截止日期 |
| `minor` | +10 | 轻微违规，措辞不当但未直接违法 | 诱导性推荐表述 |
| `info` | +5 | 建议改进，未违反法条但可优化 | 风险提示可以更醒目 |

#### 第二级：任务级别

`overall_risk_score` 是所有 `issues` 的分值之和，**封顶 100**。

**计算示例**：

```
某次审查发现 3 个问题:

  Issue 1: implied_guarantee      → severity = critical → +30 分
  Issue 2: incomplete_disclosure  → severity = major    → +20 分
  Issue 3: misleading_promotion   → severity = minor    → +10 分
  ────────────────────────────────────────────────────────
  overall_risk_score = 30 + 20 + 10 = 60
  risk_level = high (因为 60 > 50)
```

另一个示例：

```
某次审查发现 5 个问题:

  Issue 1: critical → +30
  Issue 2: critical → +30
  Issue 3: major    → +20
  Issue 4: major    → +20
  Issue 5: minor    → +10
  ──────────────────────────
  原始总分 = 110
  overall_risk_score = 100 (封顶)
  risk_level = high
```

**风险等级映射**：

| 分值区间 | risk_level | 含义 | 后续动作 |
|---------|------------|------|---------|
| 0-20 | `low` | 低风险 | 可直接通过（抽样复核） |
| 21-50 | `medium` | 中风险 | 建议人工复核 |
| 51-100 | `high` | 高风险 | 必须人工复核 |

> **注意**：后处理阶段还会根据法条引用校验结果调整分数——`verified` 的引用分值 ×1.0，`corrected` 的 ×0.8，`unverified` 的 ×0.5。参见产品设计文档第六章"风险评分计算"。

## 6. 长文档审查策略

对于基金说明书、合同等长文档（可能几万字），不能一次全部塞进 LLM。系统根据文档长度自动选择审查策略：

```
长文档审查策略:

┌──────────────────────────────────────────────────────────────────┐
│                                                                  │
│  文档总长度 < 5000 字                                             │
│  → 单次审查: 全文 + 检索上下文一次性送 LLM                        │
│                                                                  │
│  文档总长度 5000 - 30000 字                                       │
│  → 分段审查:                                                     │
│    1. 按章节/段落拆分为 chunks (每 chunk 1000-2000 字)             │
│    2. 每 chunk 独立检索上下文 + LLM 审查                          │
│    3. 合并所有 chunk 的审查结果                                   │
│    4. (可选) 最终用 LLM 做整体一致性检查                          │
│                                                                  │
│  文档总长度 > 30000 字                                            │
│  → 两阶段审查:                                                   │
│    阶段一 (快速扫描):                                             │
│      对全文做快速关键词/向量扫描，标记高风险段落                    │
│    阶段二 (深度审查):                                             │
│      只对标记的高风险段落做完整的 ACE 上下文审查                    │
│    阶段三 (完整性检查):                                           │
│      检查必备章节是否齐全 (目录级别检查)                           │
│                                                                  │
└──────────────────────────────────────────────────────────────────┘
```

### 分段审查的关键细节

| 设计要点 | 说明 |
|---------|------|
| Chunk 切分 | 优先按自然章节/段落边界切分，避免在句子中间断开。每个 chunk 保留 100 字的前后文重叠（overlap），防止边界遗漏 |
| 上下文独立检索 | 每个 chunk 独立做 ACE 五路检索。不同 chunk 可能检索到不同的法条——这是设计意图，因为不同段落涉及不同合规要点 |
| 并行审查 | 拆分后的 chunks 可以**并行**发送给 LLM，显著降低长文档总审查时间。如 10 个 chunks 并行审查，总耗时约等于单个 chunk 审查时间 |
| 结果合并 | 所有 chunk 的审查结果合并为一个完整的 ReviewResult，segment_index 按原文顺序重新编号 |
| 整体一致性检查 | 对于 > 10000 字的文档，合并后可选做一次"整体一致性 LLM 调用"——将所有发现的问题摘要送给 LLM，检查是否有遗漏或矛盾 |

## 7. 并发与性能设计

### 7.1 单次审查延迟预算

```
单次审查延迟预算:

  内容解析 (OCR/文档解析):     500ms - 3s (取决于内容类型)
  五路检索 (并行):              200ms - 500ms
  上下文组装:                    50ms
  LLM 推理:                    3s - 15s (取决于内容长度和模型)
  后处理 (法条校验等):           100ms
  ─────────────────────────────────
  总计:                         4s - 20s
```

### 7.2 各阶段延迟优化策略

| 阶段 | 主要耗时来源 | 优化手段 |
|------|-------------|---------|
| 内容解析 | OCR 模型推理 | GPU 加速；短文本跳过 OCR 直接分段 |
| 五路检索 | 向量相似度计算 | 五路**全部并行**；Milvus 使用 IVF_SQ8 索引；PostgreSQL 使用 GIN 索引；热点法条 Redis 缓存 |
| 上下文组装 | 去重 + token 计算 | 预计算法条 token 数并缓存；使用近似 token 计数 |
| LLM 推理 | 模型推理延迟 | 选用 GPT-4o 等快速模型；长内容使用流式输出；分 chunk 并行 |
| 后处理 | 法条引用校验 | 法条索引常驻内存；精确匹配走 HashMap O(1) |

### 7.3 并发能力设计

```
并发能力:

  • LLM 调用是主要瓶颈
  • 通过 LLM API 的并发限制控制
  • 长文档拆分后可并行审查各 chunk
  • 五路检索全部并行执行

  并发架构:
  ┌─────────────────────────────────────────────────────────┐
  │  Spring Boot 应用 (3+ 实例)                               │
  │                                                          │
  │  ┌──────────────────────────────────────────────────┐   │
  │  │  Semaphore-based LLM 并发控制                      │   │
  │  │                                                    │   │
  │  │  每实例 LLM 并发上限: 50 (可配置)                   │   │
  │  │  集群总并发: 50 × 3 = 150 并发 LLM 调用             │   │
  │  │                                                    │   │
  │  │  超出并发 → 排队等待 (最长等待 30s)                  │   │
  │  │  排队超时 → 返回"系统繁忙，请稍后重试"               │   │
  │  └──────────────────────────────────────────────────┘   │
  │                                                          │
  │  ┌──────────────────────────────────────────────────┐   │
  │  │  异步任务处理 (长文档)                               │   │
  │  │                                                    │   │
  │  │  长文档(> 5000字) → 提交到 RabbitMQ 异步队列         │   │
  │  │  → Worker 实例拉取并处理                             │   │
  │  │  → 处理完成通过 WebSocket 推送结果                    │   │
  │  │  → 前端轮询 + WebSocket 双通道获取结果                │   │
  │  └──────────────────────────────────────────────────┘   │
  └─────────────────────────────────────────────────────────┘
```

### 7.4 性能目标

| 指标 | 目标 | 备注 |
|------|------|------|
| 短内容审查延迟（< 1000字） | < 10s | 同步返回 |
| 中等内容审查延迟（1000-5000字） | < 20s | 同步返回，分段并行 |
| 长文档审查延迟（> 5000字） | < 60s | 异步处理，WebSocket 推送 |
| 快速过滤延迟 | < 10ms | Aho-Corasick + 必备声明检查 |
| 五路检索延迟（并行） | < 500ms | 所有检索路径并行执行 |
| 系统并发能力 | 100+ QPS | LLM API 并发为主要瓶颈 |
