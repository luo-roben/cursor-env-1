## 二、已覆盖的设计点（评审可能遗漏）

### 2.1 "缺失项"审查——不完全靠语义检索

Gemini 质疑："如果海报完全没有风险提示文字，向量检索怎么命中？"

**现有设计已覆盖这个场景，路径如下：**

```
"缺失项"的发现不走向量检索路径，走以下三条路径：

路径A（结构化查询）:
  content_type = "营销海报" → SQL 查询 → 直接命中法条:
  "所有基金营销材料必须包含风险提示"
  → 这条法条是按内容类型精确匹配的，与内容文字无关

路径E（企业必备声明）:
  企业配置了必备声明: "基金有风险，投资需谨慎"
  → 快速过滤阶段直接检查内容是否包含该声明
  → 缺失 → 标记为 missing_element

CompletenessChecker（完整性检查器）:
  按内容类型加载必备元素清单
  → 逐项检查内容是否包含
  → 缺失的进入 missing_elements 列表

这三条路径都不依赖"内容里有什么文字"来检索。
```

**但是——** 当前设计的完整性检查器 (CompletenessChecker) 的必备元素清单来源不够清晰。Gemini 建议引入的"强制自检清单"本质上是对 CompletenessChecker 的增强。**采纳。** 见第三节。

### 2.2 案例纠偏机制

05-feedback-loop.md 已有以下机制：
- 同法条驳回率 > 30% → 自动触发法条知识复核提醒
- 准确率 < 85% → 邮件提醒合规团队复核该维度
- 准确率 < 80% → 自动增加人工复核比例至 100%
- 法条失效时 → 标记 deprecated，从检索优先级降权

但缺少"关联案例批量失效"机制。**采纳黄金测试集建议**，补充定期回归检测。

### 2.3 租户级解读偏好

06-custom-rules.md 的"自然语言规则"本身就是这个功能：

```
租户A配置:
  "所有营销内容展示收益时，必须同时展示业绩比较基准，否则视为违规"
  → 这就是租户A对"业绩展示合规"的严苛解读
  → 拼入 prompt，LLM 按此标准审查

租户B没配这条 → LLM 按法条字面意思审查，标准较宽松

效果: 同一段"涨幅35%"，租户A可能判违规，租户B可能判 needs_review
```

案例库也已按 tenant_id 隔离（02-case-management.md），不存在跨租户"污染"。

### 2.4 Token 溢出截断策略

03-review-engine.md 3.1 节"合并与去重"已有明确的 token 预算和截断优先级：

```
截断优先级（从先裁剪到后裁剪）:

1. 首先裁剪: 相关度得分最低的法条 (路径C的向量检索长尾结果)
2. 然后裁剪: 案例上下文 (从10条缩减到5条)
3. 最后保留: 路径A/B的结构化查询结果 (确定性最高，不裁剪)
                + 企业自定义规则 (不裁剪)
                + 待审查原文 (不裁剪)

逻辑: 确定性匹配 > 语义匹配 > 案例参考
```

## 三、采纳的五项增强

### 增强1: 强制自检清单 (Compliance Checklist)

**问题本质：** 当前 CompletenessChecker 的必备元素清单来源模糊——文档说"存在知识库中"，但没说清楚如何构建和维护。

**增强方案：**

```
┌─────────────────────────────────────────────────────────────────┐
│  合规自检清单 (ComplianceChecklist)                                │
│                                                                  │
│  定义: 针对每种 <内容类型, 产品类型> 组合，预定义一组              │
│        "必须包含/必须满足" 的硬性检查项。                          │
│                                                                  │
│  数据来源:                                                       │
│  ① LLM 解析法条时，自动提取 norm_type = "义务" 的法条             │
│     → 这些法条描述的是"必须做什么"而不是"不能做什么"              │
│     → 自动转化为检查项                                            │
│  ② 人工确认阶段，合规人员手动添加/修改检查项                      │
│  ③ 企业自定义的必备声明（已有功能）                               │
│                                                                  │
│  示例: <营销海报, 公募基金> 的自检清单:                            │
│  ┌─────────────────────────────────────────────────────────┐    │
│  │ 检查项                       法条依据          检查方式   │    │
│  │ ─────────────────────────────────────────────────────── │    │
│  │ 包含风险提示语               第26条            语义匹配   │    │
│  │ 包含基金全称或简称           第23条            关键词     │    │
│  │ 包含基金管理人名称           第23条            关键词     │    │
│  │ 业绩数据标注截止日期(如有)   第25条            条件检查   │    │
│  │ 业绩数据标注数据来源(如有)   第25条            条件检查   │    │
│  │ 业绩数据标注比较基准(如有)   第25条            条件检查   │    │
│  │ 风险提示字号 ≥ 正文1/2       格式要求          布局分析   │    │
│  └─────────────────────────────────────────────────────────┘    │
│                                                                  │
│  执行时机: 在 LLM 审查之前和之后各执行一次                        │
│                                                                  │
│  LLM 之前 (快速过滤阶段):                                        │
│    对已能判定的检查项直接检查（如关键词匹配）                      │
│    缺失项 → 注入到 LLM prompt:                                   │
│    "注意: 系统检测到以下内容缺失，请依据对应法条给出判定:          │
│     · 未发现风险提示语（参考第26条）                               │
│     · 未发现基金管理人名称（参考第23条）"                          │
│                                                                  │
│  LLM 之后 (后处理阶段):                                          │
│    对需要语义理解的检查项由 LLM 判断                               │
│    交叉验证: LLM 是否遗漏了自检清单中的缺失项                     │
│    如果 LLM 遗漏 → 补充到 missing_elements 中                    │
│                                                                  │
│  与现有 CompletenessChecker 的关系:                               │
│    ComplianceChecklist 替代 CompletenessChecker                   │
│    更结构化、更可维护、有明确的法条依据                            │
└─────────────────────────────────────────────────────────────────┘
```

**存储位置:** PostgreSQL 新增 `compliance_checklists` 表：

| 字段 | 类型 | 说明 |
|------|------|------|
| id | BIGINT PK | 主键 |
| content_type | VARCHAR | 内容类型 |
| product_type | VARCHAR | 产品类型（nullable = 适用所有产品） |
| check_item | VARCHAR | 检查项描述 |
| check_method | ENUM | keyword / semantic / layout / conditional |
| law_article_id | BIGINT FK | 关联的法条依据 |
| condition | VARCHAR | 触发条件（如"仅当内容包含业绩数据时"） |
| severity_if_missing | ENUM | critical / major / minor |
| enabled | BOOLEAN | 是否启用 |
| tenant_id | BIGINT FK | 租户级覆盖（null = 全局） |

### 增强2: 法条锚点验证（ID回填方案）

**问题本质：** 当前的防幻觉机制是"LLM 输出法条内容 → 后处理校验"。但 LLM 可能输出一个正确的编号配上错误的内容，三级校验可能漏过。

**增强方案：改为 LLM 只输出 ID，系统强制回填原文。**

```
┌─────────────────────────────────────────────────────────────────┐
│  法条锚点验证 — 升级后的流程                                       │
│                                                                  │
│  当前方案 (已有):                                                 │
│  LLM 输出: law_reference: {                                     │
│    article_id: "第24条第1款第2项",                                │
│    law_name: "基金销售管理办法",                                   │
│    original_text: "不得以保本...方式宣传"  ← LLM 自己写的          │
│  }                                                               │
│  后处理: 校验 article_id 是否存在 → 存在则通过                     │
│  风险: LLM 可能编号对但内容张冠李戴                                │
│                                                                  │
│  升级方案:                                                       │
│  LLM 输出: law_reference: {                                     │
│    article_id: "第24条第1款第2项",                                │
│    law_name: "基金销售管理办法"                                   │
│    // 不再输出 original_text                                     │
│  }                                                               │
│  后处理:                                                         │
│    ① 用 article_id + law_name 查知识库                           │
│    ② 命中 → 从知识库取出 original_text（人工确认过的原文）         │
│       → 强制回填到审查结果中                                      │
│    ③ 未命中 → 标记 unverified，提升复核优先级                     │
│    ④ 最终报告中的法条原文 100% 来自知识库，不来自 LLM             │
│                                                                  │
│  Prompt 调整:                                                    │
│  "引用法条时，只需输出法条编号(article_id)和法律简称(law_name)，   │
│   不需要输出法条原文。系统会自动回填。"                            │
│  → 减少 LLM 输出的 token 数                                     │
│  → 彻底消除法条内容被编造的可能                                   │
│                                                                  │
│  UI 展示:                                                        │
│  ┌───────────────────────┬───────────────────────────────────┐  │
│  │  违规内容              │  法条依据                          │  │
│  │                       │                                   │  │
│  │  "现在买入，亏损概率   │  《基金销售管理办法》              │  │
│  │   很小"                │  第24条第1款第2项                  │  │
│  │                       │                                   │  │
│  │  ← 原文高亮            │  "不得以保本、保收益或者承诺       │  │
│  │                       │   最低收益等方式宣传、介绍          │  │
│  │                       │   基金产品"                        │  │
│  │                       │                                   │  │
│  │                       │  ← 来自知识库，不是 LLM 写的       │  │
│  └───────────────────────┴───────────────────────────────────┘  │
└─────────────────────────────────────────────────────────────────┘
```

### 增强3: 长文档多智能体协作

**问题本质：** 分段审查丢失全局视野。第5页的承诺和第50页的风险提示可能矛盾。

**增强方案：在现有分段策略上叠加"摘要+终审"层。**

```
长文档审查策略 — 升级为三智能体协作:

┌──────────────────────────────────────────────────────────────┐
│  Agent 1: 分段审查专家 (已有，不改)                            │
│                                                               │
│  每个 chunk 独立做 ACE 检索 + LLM 审查                        │
│  输出: 每段的违规/合规判定                                     │
│  特点: 关注细节，看不到全貌                                    │
└──────────────────────┬───────────────────────────────────────┘
                       │
                       ▼
┌──────────────────────────────────────────────────────────────┐
│  Agent 2: 文档摘要专家 (新增)                                  │
│                                                               │
│  输入: 全文（或全文的章节标题+关键段落）                        │
│  任务: 提取文档的全局关键参数:                                  │
│    · 产品名称/类型/风险等级                                    │
│    · 承诺的收益目标/投资策略                                   │
│    · 风险揭示的位置和充分程度                                  │
│    · 费率结构                                                  │
│    · 各章节的核心结论                                          │
│  输出: 结构化的文档摘要 (约 500-1000 tokens)                   │
│  特点: 看得到全貌，不关注细节                                  │
└──────────────────────┬───────────────────────────────────────┘
                       │
                       ▼
┌──────────────────────────────────────────────────────────────┐
│  Agent 3: 终审一致性检查专家 (新增)                             │
│                                                               │
│  输入:                                                        │
│    · Agent 1 的所有审查结果（各段落的违规判定）                 │
│    · Agent 2 的文档摘要（全局参数）                            │
│  任务:                                                        │
│    · 检查前后矛盾（如标题说"稳健"但投资策略含高杠杆）          │
│    · 检查遗漏（摘要发现了收益承诺但分段审查没标出违规）         │
│    · 检查法条引用一致性（同一问题在不同段落引用了矛盾法条）     │
│  输出: 一致性检查报告，补充到最终审查结果中                    │
│  特点: 交叉验证，发现段落间的逻辑矛盾                         │
│                                                               │
│  触发条件: 仅文档 > 10000 字时触发                             │
│  短文档(海报/推文)不需要，避免不必要的 LLM 调用                 │
└──────────────────────────────────────────────────────────────┘
```

**Agent 2 和 Agent 3 可以合并为一次 LLM 调用**，实际实现不一定需要三个独立的 LLM 调用。可以在分段审查全部完成后，做一次"全局审查"，输入是分段审查的结论摘要 + 文档目录/关键段落，LLM 做一致性和完整性检查。

### 增强4: 法条效力层级与重排 (Reranking)

**问题本质：** 当多条法条适用于同一违规行为时，应该引用效力最高、最新的那条，而不是语义最接近的那条。

**增强方案：在 law_articles 表增加效力层级字段，检索结果做效力加权重排。**

在 `law_articles` 表增加字段:

| 字段 | 类型 | 说明 |
|------|------|------|
| authority_level | INT | 效力层级: 1=法律 2=行政法规 3=部门规章 4=规范性文件 5=自律规则 6=监管问答 |
| effective_date | DATE | 生效日期 |
| expiry_date | DATE | 失效日期（null = 永久有效） |
| is_current | BOOLEAN | 是否为现行有效版本（自动根据 expiry_date 和 supersedes 计算） |

检索结果的重排公式:

```
最终排序分 = RRF_score × authority_weight × freshness_weight × validity_weight

authority_weight:
  法律(1级):       × 1.5
  行政法规(2级):   × 1.3
  部门规章(3级):   × 1.2
  规范性文件(4级): × 1.0
  自律规则(5级):   × 0.9
  监管问答(6级):   × 0.8

freshness_weight:
  最近1年内发布:   × 1.2
  1-3年前发布:     × 1.0
  3年以上:         × 0.9

validity_weight:
  现行有效:        × 1.0
  已修改(有替代):  × 0.3  (仍可参考但不应作为主要依据)
  已废止:          × 0.0  (直接过滤)
```

**效果：** 同一违规行为，如果行业自律准则和国家法律都匹配上了，国家法律会排在前面。新法优于旧法。已废止的法条不会出现在审查结果中。

### 增强5: 黄金测试集与漂移监控

**问题本质：** "越用越准"的闭环有反向风险——如果人工复核出现偏差，系统可能学歪。

**增强方案：**

```
┌─────────────────────────────────────────────────────────────────┐
│  黄金测试集 (Golden Dataset)                                      │
│                                                                  │
│  构成:                                                           │
│  · 50 条明确违规样本 (含各种违规类型)                              │
│  · 30 条明确合规样本 (含容易误判的边界场景)                        │
│  · 20 条疑似违规样本 (合理的分歧空间，标注"可接受答案区间")        │
│                                                                  │
│  来源:                                                           │
│  · 由最资深的合规官团队 (≥3人) 独立评审并取共识                    │
│  · 每条附: 标准答案 + 引用法条 + 判定理由                         │
│                                                                  │
│  使用方式:                                                       │
│  ┌────────────────────────────────────────────────────────┐     │
│  │  自动回归测试 (每周一次 / 每次知识库更新后)              │     │
│  │                                                        │     │
│  │  1. 对 100 条样本执行完整审查流程                       │     │
│  │  2. 对比 LLM 输出 vs 标准答案                          │     │
│  │  3. 计算指标:                                          │     │
│  │     · 准确率 (总体正确比例)                             │     │
│  │     · 召回率 (违规样本的识别率 — 最重要)                │     │
│  │     · 精确率 (判定违规中真正违规的比例)                  │     │
│  │     · 法条引用匹配率                                   │     │
│  │                                                        │     │
│  │  4. 报警阈值:                                          │     │
│  │     · 召回率 < 90% → 红色报警，暂停自动通过             │     │
│  │     · 准确率 < 85% → 黄色报警，增加人工复核比例         │     │
│  │     · 法条匹配率 < 80% → 触发知识库检查                 │     │
│  │                                                        │     │
│  │  5. 与法条更新联动:                                    │     │
│  │     · 法条失效 → 自动检查黄金测试集中引用该法条的样本    │     │
│  │     → 标记为"需更新标准答案"                            │     │
│  │     → 通知合规官更新                                   │     │
│  └────────────────────────────────────────────────────────┘     │
│                                                                  │
│  法条失效时的关联处理:                                            │
│  · 法条标记 deprecated                                           │
│  · 自动查询: SELECT * FROM review_cases                          │
│    WHERE law_references @> '[{"article_id": "被废止的法条ID"}]'   │
│  · 匹配的案例标记为 "law_deprecated"                             │
│  · 这些案例在检索时降权但不删除(可能仍有参考价值)                  │
│  · 通知合规团队复核这批案例                                       │
└─────────────────────────────────────────────────────────────────┘
```

## 四、需权衡的设计取舍

### 4.1 "Lost in the Middle" 问题

Gemini 提到 LLM 可能忽略 prompt 中间的法条。这是一个已知的学术问题。

**应对策略：**

```
不通过技术手段解决，通过 Prompt 结构优化缓解:

1. 最相关的法条放在最前面和最后面（符合 LLM 的注意力 U 型分布）
2. 法条上下文不堆砌原文，而是压缩为结构化摘要:
   "【第24条①】禁止: 以预期收益率宣传 | 违规例: 预期年化12%"
   → 每条法条约 30-50 tokens，比贴原文(100-200 tokens)短得多
   → 50 条法条 × 40 tokens = ~2000 tokens，在注意力范围内
3. 用"=== 适用法规 ==="这样的分隔符做视觉分区
4. 在 prompt 末尾重申: "必须检查以上所有法条"
```

### 4.2 MVP 阶段要不要做案例检索？

Gemini 建议 Phase 1 不做案例检索。

**我的判断：Phase 1 不做自动案例沉淀，但预置一批种子案例。**

```
Phase 1 策略:

× 不做: 自动案例沉淀（审查→反馈→入库→增强）
  → 闭环机制在 Phase 2 做

√ 要做: 预置种子案例库
  → 手动整理 200-500 条典型违规/合规案例
  → 直接导入案例库
  → 审查时可被检索到
  → 相当于给 LLM 提供了 few-shot examples

理由:
  案例的存在显著提升 LLM 判断的一致性和准确性
  没有案例 → LLM 在边界场景的判断高度不稳定
  有案例 → LLM 能参照先例做出更一致的判断
```

### 4.3 Phase 1 的准确率预期

```
无案例、仅靠法条检索: 预期准确率 ~75-80%
  主要失分点: 边界场景判断不一致、漏检、过度审查

有种子案例库(200-500条): 预期准确率 ~85-88%
  案例提供了判断锚点，减少边界场景的波动

有反馈闭环(Phase 2+): 预期准确率 ~90-95%
  持续沉淀纠正 LLM 的判断偏差

这些数字需要通过 Gemini 建议的 "Manual RAG Test" 来验证
```

## 五、不采纳的建议及理由

### 5.1 不做 Fine-tuning

```
不采纳理由:

1. RAG 已经足够: 法规知识通过检索注入，不需要"记忆"在模型权重里
2. 更新困难: 法规频繁更新，微调模型无法及时跟进；更新知识库即时生效
3. 可审计性: RAG 模式每次审查的依据是明确的检索结果，可追溯；
   微调模型的判断依据是不可解释的权重
4. 多模型灵活性: 当前设计可以随时切换底座模型(GPT-4o → Claude → DeepSeek)，
   微调后就锁定在一个模型上
5. 成本: 每次法规更新都要重新微调，成本远高于更新知识库
```

### 5.2 不做"敏感度调节滑块"

```
不采纳理由:

1. 合规是法律问题，不是概率问题。"违规"就是"违规"，不应该有"调低敏感度"的操作
2. 如果企业想"宽松一点"，应该通过自然语言规则精确描述宽松到什么程度
   → 例如: "历史收益数据即使未标注来源，如果标注了截止日期，可降为建议级别"
3. 滑块让非专业用户产生"可以调低合规标准"的错误预期
4. 已有的复核策略(全量/风险驱动/抽样)实际上就是"敏感度"的合理实现
```

## 六、回应五个关键追问

### Q1: 海报完全没有风险提示，ACE 怎么发现？

**答：不靠 ACE 的向量检索发现，靠三个硬机制：**
1. 路径A结构化查询 → 按内容类型命中"营销材料必须包含风险提示"的法条
2. 企业必备声明检查 → 快速过滤阶段直接检测
3. 合规自检清单（新增）→ 预定义的 checklist 逐项检查

这三个都不需要内容里有相关文字。

### Q2: 上位法与下位法、一般法与特殊法的优先级？

**答：通过效力层级字段 + 重排公式解决。**
- law_articles 新增 `authority_level` 字段（1=法律 到 6=监管问答）
- 检索结果按 RRF 排序后，再乘以效力权重
- 法律 > 行政法规 > 部门规章 > 自律规则
- 新法优于旧法（freshness_weight）
- 已废止法条直接过滤（validity_weight = 0）

### Q3: 如何防止 LLM 伪造法条内容？

**答：LLM 只输出法条 ID，系统从知识库回填原文。**
- Prompt 明确指令："引用法条只需输出编号和法律名称"
- 后处理阶段用 ID 查知识库，取出人工确认过的原文
- 最终报告中的法条原文 100% 来自知识库
- 未查到的 ID → 标记 unverified → 提升人工复核优先级

### Q4: 50 页说明书如何保证审查连贯性？

**答：三智能体协作——分段专家 + 摘要专家 + 终审一致性检查。**
- 分段专家：每 chunk 独立审查（已有）
- 摘要专家：提取全局关键参数（新增）
- 终审专家：拿摘要 + 分段结论做交叉验证，发现前后矛盾（新增）
- 仅文档 > 10000 字时触发终审专家

### Q5: Phase 1 无案例时准确率多少？如何防过度审查？

**答：预置种子案例库，不完全"冷启动"。**
- Phase 1 手动导入 200-500 条种子案例
- 有种子案例：预期准确率 ~85-88%
- 防过度审查：案例库包含"合规案例"（边界场景判合规的先例），防止 LLM 把所有边界场景都判违规
- 用黄金测试集每周监控，发现过度审查趋势及时干预

## 附: Gemini 建议的 "Manual RAG Test" — 采纳

在开始编码前，先手动验证 RAG + LLM 审查的可行性：

```
Manual RAG Test 步骤:

1. 准备: 手动整理 50 条核心法条 + 50 条测试样本
2. 手动模拟检索: 对每个测试样本，人工挑选最相关的 5-10 条法条

6. 调优: 根据结果优化 prompt 模板和法条摘要格式

通过标准:
  · 50 条样本中违规判定的召回率 > 85%

  · 无严重误判（将明显合规内容判为 critical 违规）

如果不通过:
  · 优化法条结构化格式（加更多违规示例/语义延伸）
  · 优化 prompt 模板（更明确的审查指令）
  · 考虑增加案例数量

```
