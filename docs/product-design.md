## 一、系统定位与核心理念

### 1.1 一句话定位

**用 LLM 代替人工阅读法律法规，用 RAG 检索代替手动规则路由，用案例沉淀代替规则维护，构建一个"越用越准"的智能合规审查引擎。**

### 1.2 核心设计原则

| 序号 | 原则 | 说明 |
|------|------|------|
| P1 | **机器读法律，人只做确认** | 法律法规由 LLM 自动解析为结构化知识，人工只做 review & approve |
| P2 | **语义检索，不靠标签** | 审查时按内容语义从知识库检索相关法条，不维护"内容类型→规则集"的手动映射 |
| P3 | **每次审查动态组装上下文** | ACE 架构：根据当前审查的内容类型、产品类型、渠道，实时检索法条+案例组装 prompt |
| P4 | **越用越准** | 每次人工复核的结果沉淀为新案例，持续增强知识库 |
| P5 | **可溯源** | 每条审查结论必须附上法条原文引用，可追溯、可审计 |
| P6 | **简单自定义** | 企业用自然语言描述要求，不写规则、不选标签、不配引擎 |

### 1.3 与传统方案的根本性差异

```
❌ 传统方案（Drools/正则驱动）:
法律法规文本 → 人工阅读 → 人工总结规则 → 人工写 DRL/正则 → 人工维护标签映射
                ↑ 几百部法律、几千条法条，人工根本写不完，也维护不了

✅ 本系统方案（LLM + RAG 驱动）:
法律法规文本 → LLM 自动解析 → 结构化知识入库 → 审查时 LLM 基于检索到的知识做判断
                ↑ 机器读法律，人只做最终确认；知识库自动扩展，无需手动维护
```

## 三、知识构建层 — "让机器读懂法律"

### 3.1 法律法规采集

#### 3.1.1 数据来源

| 来源分类 | 具体来源 | 采集方式 | 更新频率 |
|----------|----------|----------|----------|
| 国家法律 | 全国人大法规库、国家法律法规数据库 | 爬虫 + RSS | 实时监控 |
| 部门规章 | 证监会、银保监会、人民银行官网 | 爬虫 + API | 每日检查 |
| 行业自律 | 基金业协会、证券业协会 | 爬虫 | 每日检查 |
| 监管问答 | 证监会监管问答、窗口指导 | 人工导入 + 爬虫 | 发布即采集 |
| 处罚公告 | 各地证监局、央行分行 | 爬虫 | 每日检查 |
| 商业数据库 | 北大法宝、威科先行 | API 对接 | 按合同更新 |
| 内部制度 | 企业自有合规制度文档 | 人工上传 | 按需 |

#### 3.1.2 采集流水线


### 3.2 LLM 结构化解析引擎

#### 3.2.1 解析流程

```
法规原文
    │
    ▼
┌─────────────────────────────────────────────────────────┐
│  阶段1: 法条拆分                                        │
│                                                         │
│  输入: 法规全文                                          │
│  处理: LLM 按"条-款-项"拆分为独立法条单元                 │
│  输出: 法条列表，每条保留完整上下文                        │
│                                                         │
│  Prompt 要点:                                           │
│  "请将以下法规文本按'条-款-项'结构拆分。                   │
│   每个最小单元保留其所属的条、款编号，                     │
│   以及适用于该单元的主语（如果主语在上文）。               │
│   保持原文不要改写。"                                    │
└────────────────────────┬────────────────────────────────┘
                         │
                         ▼
┌─────────────────────────────────────────────────────────┐
│  阶段2: 语义结构化                                       │
│                                                         │
│  输入: 单条法条文本                                       │
│  处理: LLM 提取结构化信息                                 │
│  输出: 结构化 JSON                                       │
│                                                         │
│  Prompt 要点:                                           │
│  "请将以下法条解析为结构化 JSON，包含:                     │
│   - norm_type: 禁止/义务/权利/定义/程序                   │
│   - subject: 规范约束的主体                               │
│   - behavior: 被禁止/要求的行为                           │
│   - object: 行为作用的对象                                │
│   - condition: 适用条件/前提                              │
│   - applicable_scenarios: 适用场景列表                    │
│   - applicable_content_types: 适用的内容形式              │
│   - applicable_product_types: 适用的产品类型              │
│   - key_phrases: 法条中的关键词/短语                      │
│   - semantic_extensions: 语义延伸(隐含的违规变体)         │
│   - violation_examples: 违规表述示例(3-5个)               │
│   - compliant_examples: 合规表述示例(1-3个)               │
│   - penalty: 违反后果                                    │
│   - related_articles: 关联法条                            │
│  "                                                      │
└────────────────────────┬────────────────────────────────┘
                         │
                         ▼
┌─────────────────────────────────────────────────────────┐
│  阶段3: 向量化与索引                                     │
│                                                         │
│  对每条法条知识生成多种粒度的 Embedding:                   │
│                                                         │
│  • 法条原文 Embedding (用于精确法条检索)                   │
│  • 行为描述 Embedding (用于审查时语义匹配)                 │
│  • 违规示例 Embedding (用于与待审查内容匹配)               │
│  • 语义延伸 Embedding (用于捕捉变体表述)                   │
│                                                         │
│  Embedding 模型: bge-large-zh-v1.5 或 m3e-large          │
│  维度: 1024                                               │
│  存储: Milvus Collection, 按法规来源分 Partition            │
└────────────────────────┬────────────────────────────────┘
                         │
                         ▼
┌─────────────────────────────────────────────────────────┐
│  阶段4: 知识图谱构建                                     │
│                                                         │
│  实体:                                                   │
│  • Law (法律)                                            │
│  • Article (法条)                                        │
│  • Subject (规范主体: 如"基金销售机构")                    │
│  • Behavior (规范行为: 如"以预期收益宣传")                 │
│  • ProductType (产品类型: 如"公募基金")                    │
│  • ContentType (内容类型: 如"营销海报")                    │
│                                                         │
│  关系:                                                   │
│  • Law -[CONTAINS]-> Article                             │
│  • Article -[CONSTRAINS]-> Subject                       │
│  • Article -[PROHIBITS/REQUIRES]-> Behavior              │
│  • Article -[APPLIES_TO]-> ProductType                   │
│  • Article -[APPLIES_TO]-> ContentType                   │
│  • Article -[REFERENCES]-> Article (法条间交叉引用)       │
│  • Article -[SUPERSEDED_BY]-> Article (新旧法条替代关系)   │
└─────────────────────────────────────────────────────────┘
```

#### 3.3.2 案例向量化策略

```
每条案例生成 3 种 Embedding:

1. 审查内容 Embedding — original_text 的向量
   用途: 审查时用待审内容检索相似案例

2. 违规理由 Embedding — reason 的向量
   用途: 按违规模式检索相似案例

3. 组合 Embedding — original_text + verdict + reason 拼接后的向量
   用途: 综合语义检索
```

| **合计** | | **~3,500 条结构化知识** |

补充数据量：
- 企业历史审核案例（参考盈米的 80,000+）→ 向量索引，按需检索
- 企业自定义要求 → 每个租户几十到几百条
- 向量库总条目（含多粒度向量）→ ~15,000 - 20,000 条向量

**关键认知：这 3,500 条是知识库条目，不是 Drools 规则。审查时 LLM 从中检索相关的几十条作为上下文，而不是全部加载。**

### 4.3 长文档审查策略

对于基金说明书、合同等长文档（可能几万字），不能一次全部塞进 LLM：

```
长文档审查策略:

┌──────────────────────────────────────────────────────────────────┐
│                                                                  │
│  文档总长度 < 5000 字                                             │
│  → 单次审查: 全文 + 检索上下文一次性送 LLM                        │
│                                                                  │
│  文档总长度 5000 - 30000 字                                       │
│  → 分段审查:                                                     │
│    1. 按章节/段落拆分为 chunks (每 chunk 1000-2000 字)             │
│    2. 每 chunk 独立检索上下文 + LLM 审查                          │
│    3. 合并所有 chunk 的审查结果                                   │
│    4. (可选) 最终用 LLM 做整体一致性检查                          │
│                                                                  │
│  文档总长度 > 30000 字                                            │
│  → 两阶段审查:                                                   │
│    阶段一 (快速扫描):                                             │
│      对全文做快速关键词/向量扫描，标记高风险段落                    │
│    阶段二 (深度审查):                                             │
│      只对标记的高风险段落做完整的 ACE 上下文审查                    │
│    阶段三 (完整性检查):                                           │
│      检查必备章节是否齐全 (目录级别检查)                           │
│                                                                  │
└──────────────────────────────────────────────────────────────────┘
```

```
  总计:                         4s - 20s

并发能力:
  • LLM 调用是主要瓶颈
  • 通过 LLM API 的并发限制控制
  • 长文档拆分后可并行审查各 chunk
  • 五路检索全部并行执行
```

## 五、内容路由与差异化处理

### 5.1 核心洞察

**法条检索不依赖预设的"内容类型→规则集"映射，内容的语义本身决定了检索到哪些法条。**

例如：
- 海报里写了"收益率20%" → 向量搜索自然命中第24条
- 说明书里缺少"风险揭示章节" → 向量搜索命中信息披露法条
- 物料里写了"最好的基金" → 向量搜索命中广告法第9条（极限词）

### 5.3 各内容类型的详细差异化处理

| 内容类型 | 解析方式 | 特有检查维度 | 法定要求示例 |
|----------|----------|-------------|-------------|
| **图片/海报** | OCR + 布局分析（字号检测、位置识别） | 风险提示字号是否足够大？位置是否醒目？ | 风险提示文字不得小于最大字号的1/2 |
| **PDF/说明书** | 文档结构解析 + 目录提取 + 章节拆分 | 法定必备章节是否齐全？目录完整性？ | 基金招募说明书必须包含"风险揭示"独立章节 |
| **纯文本/推文** | 直接分段 | 是否包含风险提示语？字数是否超限？ | 微信推文需包含免责声明 |
| **视频/直播** | 关键帧 OCR + 语音转写 | 口头表述合规性、字幕内容、画面中的文字 | 直播中不得口头承诺收益 |
| **H5/网页** | HTML 解析 + 截图 + 链接追踪 | 页面跳转是否合规？弹窗内容？ | 基金购买页面必须展示风险等级匹配提示 |

## 六、审查结果后处理与防幻觉

### 6.1 法条引用校验器 (CitationVerifier)

LLM 审查最大的风险是**编造不存在的法条**。系统必须对每条法条引用做校验：

```
LLM 返回的每条法条引用
          │
          ▼
┌──────────────────────────────────────────────────────────────┐
│  CitationVerifier                                             │
│                                                               │
│  Step 1: 精确匹配                                             │
│    查询知识库:                                                 │
│    SELECT * FROM law_articles                                 │
│    WHERE article_id = :llm_cited_article_id                   │
│    AND law_name LIKE :llm_cited_law_name                      │
│                                                               │
│    如果命中 → 校验通过 ✅                                      │
│    如果未命中 → 进入 Step 2                                   │
│                                                               │
│  Step 2: 模糊匹配                                             │
│    可能 LLM 用了简称或略有不同的编号:                           │
│    例: LLM 说 "第24条第3款" 但实际只有第1款                    │
│                                                               │
│    查询:                                                      │
│    SELECT * FROM law_articles                                 │
│    WHERE law_name LIKE :fuzzy_law_name                        │
│    AND article_id LIKE '第24条%'                              │
│                                                               │
│    如果找到相似法条 → 替换引用并标记 "引用已修正" ⚠️            │
│    如果完全找不到 → 进入 Step 3                                │
│                                                               │
│  Step 3: 幻觉标记                                             │
│    该引用标记为 "无法验证的引用" ❌                             │
│    在审查结果中:                                               │
│    - 保留 LLM 的违规判断和理由                                 │
│    - 法条引用标记为 "未经验证，需人工确认"                      │
│    - 提升该条目的人工复核优先级                                │
│                                                               │
│  输出: 校验后的法条引用列表，每条附状态:                        │
│    verified / corrected / unverified                          │
└──────────────────────────────────────────────────────────────┘
```

### 6.2 风险评分计算

```
风险评分 (0-100) 计算规则:

  基础分 = 0 (无违规)

  每发现一条违规:
    critical (严重违规，如保本承诺): +30
    major (重要违规，如数据缺失):    +20
    minor (轻微违规，如措辞不当):    +10
    info (建议，如可优化的表述):      +5

  加权因子:
    如果法条引用状态为 verified:     × 1.0
    如果法条引用状态为 corrected:    × 0.8
    如果法条引用状态为 unverified:   × 0.5

  缺失必备元素:
    每缺失一项 critical 元素:       +25
    每缺失一项 recommended 元素:    +10

  封顶: 100

  风险等级:
    0-20:   低风险 (low)     → 绿色，可直接通过
    21-50:  中风险 (medium)  → 黄色，建议人工复核
    51-100: 高风险 (high)    → 红色，必须人工复核
```

#### 7.2.2 单条复核操作

对于 LLM 给出的每一条判定，人工复核人员可以执行以下操作：

```
┌─────────────────────────────────────────────────────────────────────┐
│  复核操作详情                                                        │
│                                                                      │
│  LLM 判定: 段落4 "亏损概率很小" → 违规 (保本暗示)                    │
│  法条引用: 第24条第1款第2项 ✅已验证                                  │
│                                                                      │
│  ┌───────────────────────────────────────────────────────────────┐  │
│  │  复核人操作选项:                                               │  │
│  │                                                               │  │
│  │  ┌──────────────────────────────────────────────────────┐    │  │
│  │  │ ① 确认 (Confirm)                                     │    │  │
│  │  │   "同意 LLM 的判定，该内容确实违规"                    │    │  │
│  │  │   → 系统行为:                                         │    │  │
│  │  │     · 审查结果标记为 human_confirmed = true            │    │  │
│  │  │     · 生成一条新案例: verdict=violation, confirmed     │    │  │
│  │  │     · 案例入库，可被后续审查检索                        │    │  │
│  │  └──────────────────────────────────────────────────────┘    │  │
│  │                                                               │  │
│  │  ┌──────────────────────────────────────────────────────┐    │  │
│  │  │ ② 驳回 (Reject)                                      │    │  │
│  │  │   "不同意 LLM 的判定，该内容实际合规"                   │    │  │
│  │  │   → 必填: 驳回理由                                    │    │  │
│  │  │     例: "在特定上下文中，'概率小'是对客观事实的陈述，    │    │  │
│  │  │          不构成保本承诺"                               │    │  │
│  │  │   → 系统行为:                                         │    │  │
│  │  │     · 审查结果标记为 human_rejected = true             │    │  │
│  │  │     · 生成一条新案例: verdict=compliant (纠错案例)     │    │  │
│  │  │     · 案例入库，帮助 LLM 在相似场景下做出正确判断       │    │  │
│  │  │     · 纠错案例在后续检索中权重 +20% (高价值案例)       │    │  │
│  │  └──────────────────────────────────────────────────────┘    │  │
│  │                                                               │  │
│  │  ┌──────────────────────────────────────────────────────┐    │  │
│  │  │ ③ 修改 (Modify)                                      │    │  │
│  │  │   "部分同意，但需要调整判定内容"                        │    │  │
│  │  │   → 可修改: 严重程度 / 法条引用 / 修改建议 / 违规理由  │    │  │

│  │  │   → 系统行为:                                         │    │  │
│  │  │     · 保存修改后的版本                                 │    │  │
│  │  │     · 生成修正案例: 保留原始 LLM 判定 + 人工修正版     │    │  │
│  │  │     · 两个版本都入库，供系统学习"应该调整的方向"        │    │  │
```

### 7.4 案例如何被使用 — 在审查中的作用

```
下一次审查时:

用户提交: "该基金亏损风险较低"

  → 向量检索案例库:
    命中案例 CASE-2024-00012345:
      原文: "亏损概率很小"
      判定: violation (人工确认)
      理由: 构成暗示保本

    命中案例 CASE-2024-00012400:
      原文: "本基金属于中低风险产品"
      判定: compliant (人工确认)
      理由: 客观描述产品风险等级，不构成保本承诺

  → 两条案例一起放入 LLM 的 prompt:
    LLM 看到:
    - "亏损概率很小" 被判违规
    - "属于中低风险产品" 被判合规
    - 当前要审查: "亏损风险较低"

    LLM 的判断会更精准:
    "亏损风险较低"更接近"亏损概率很小"的表述模式，
    构成对风险的弱化暗示，应判定为违规。
```

## 十、快速过滤器（原 Drools 层降级）

### 10.1 定位

快速过滤器是 LLM 审查之前的**轻量级预处理层**，用于拦截最明显的违规，减少 LLM 调用量。

### 10.2 实现

```
┌─────────────────────────────────────────────────────────────────┐
│  QuickFilter — 快速过滤器                                        │
│                                                                  │
│  位置: LLM 审查之前                                               │
│  耗时: < 10ms                                                    │
│  实现: 纯 Java 代码, 无外部引擎依赖                                │
│                                                                  │
│  ┌──────────────────────────────────────────────────────────┐   │
│  │  检查1: 禁用词匹配                                       │   │
│  │  引擎: Aho-Corasick 自动机                                │   │
│  │  输入: 内容全文 + 租户禁用词表                             │   │
│  │  输出: 命中的禁用词列表                                   │   │
│  │                                                          │   │
│  │  命中 → 标记 issue (禁用词违规), 继续后续检查              │   │
│  │  未命中 → 跳过                                            │   │
│  └──────────────────────────────────────────────────────────┘   │
│                                                                  │
│  ┌──────────────────────────────────────────────────────────┐   │
│  │  检查2: 必备声明检查                                      │   │
│  │  引擎: String.contains (精确) / Embedding 相似度 (语义)   │   │
│  │  输入: 内容全文 + 租户必备声明列表                         │   │
│  │  输出: 缺失的声明列表                                     │   │
│  │                                                          │   │
│  │  缺失 → 标记 missing_element                             │   │
│  └──────────────────────────────────────────────────────────┘   │
│                                                                  │
│  ┌──────────────────────────────────────────────────────────┐   │
│  │  检查3: 格式/元信息校验                                   │   │
│  │  · 文件大小是否超限                                       │   │
│  │  · 文件格式是否支持                                       │   │
│  │  · 内容是否为空                                           │   │
│  └──────────────────────────────────────────────────────────┘   │
│                                                                  │
│  快速过滤结果:                                                    │
│  · 发现的问题合并到最终审查结果中                                  │
│  · 无论是否发现问题，都继续进入 LLM 深度审查                       │
│    (除非内容为空/格式不支持等前置错误)                              │
│                                                                  │
│  注意: Drools 不用。                                               │
│  禁用词匹配 → Aho-Corasick (O(n), 比 Drools 更快更简单)          │
│  必备声明 → String.contains / Embedding                           │
│  不存在复杂的条件推理链需求                                        │
└─────────────────────────────────────────────────────────────────┘
```

## 附录

### A. 关键问题答疑

**Q: 几百条规则怎么够？国家那么多法律法规**

A: 不是几百条规则，是几千条结构化法条知识，由 LLM 自动从法律原文解析生成，人只做确认。每条法条解析为包含原文、语义延伸、违规示例等的完整知识条目，远比 Drools 规则表达力更强。

**Q: 标签维护的工作量问题**

A: 新方案不用人工打标签。法条知识做了 Embedding 向量化存储，审查时按内容语义自动检索匹配的法条，不靠"内容类型→规则集"的人工映射。

**Q: 让客户配规则太复杂**

A: 客户只需配四样东西：禁用词（直接敲词）、必备声明（直接贴文字）、产品信息（填表单）、自然语言要求（用人话写）。不需要写正则、选标签、配引擎。

**Q: LLM 会不会编造法条？**

A: 会，所以有法条引用校验器 (CitationVerifier)。LLM 引用的每条法条都与知识库做精确/模糊匹配校验，未验证的引用会标记并提升人工复核优先级。

**Q: 性能够吗？LLM 调用很慢**

A: 短内容 < 10s，长文档 < 60s（分 chunk 并行）。快速过滤 < 10ms，向量检索 < 200ms。LLM 是主要瓶颈，通过分段并行和缓存热点知识优化。

### B. 术语表

| 术语 | 说明 |
|------|------|
| ACE | Agentic Context Engineering, 每次审查动态组装最优上下文的架构模式 |
| RAG | Retrieval-Augmented Generation, 检索增强生成 |
| Embedding | 将文本转换为高维向量表示，用于语义相似度计算 |
| 知识图谱 | 用图结构表示法律实体和关系的数据库 |
| 法条知识 | 从法律条文中结构化提取的知识单元 |
| 案例沉淀 | 将人工审核结果转化为可被系统学习的案例数据 |
| 防幻觉 | 防止 LLM 编造不存在的法律条文或虚假信息 |
| 快速过滤 | LLM 之前的轻量级规则匹配层 |
