### 5.2.2 单条复核操作

对于 LLM 给出的每一条判定，人工复核人员可以执行以下操作：

```
┌─────────────────────────────────────────────────────────────────────┐
│  复核操作详情                                                        │
│                                                                      │
│  LLM 判定: 段落4 "亏损概率很小" → 违规 (保本暗示)                    │
│  法条引用: 第24条第1款第2项 ✅已验证                                  │
│                                                                      │
│  ┌───────────────────────────────────────────────────────────────┐  │
│  │  复核人操作选项:                                               │  │
│  │                                                               │  │
│  │  ┌──────────────────────────────────────────────────────┐    │  │
│  │  │ ① 确认 (Confirm)                                     │    │  │
│  │  │   "同意 LLM 的判定，该内容确实违规"                    │    │  │
│  │  │   → 系统行为:                                         │    │  │
│  │  │     · 审查结果标记为 human_confirmed = true            │    │  │
│  │  │     · 生成一条新案例: verdict=violation, confirmed     │    │  │
│  │  │     · 案例入库，可被后续审查检索                        │    │  │
│  │  └──────────────────────────────────────────────────────┘    │  │
│  │                                                               │  │
│  │  ┌──────────────────────────────────────────────────────┐    │  │
│  │  │ ② 驳回 (Reject)                                      │    │  │
│  │  │   "不同意 LLM 的判定，该内容实际合规"                   │    │  │
│  │  │   → 必填: 驳回理由                                    │    │  │
│  │  │     例: "在特定上下文中，'概率小'是对客观事实的陈述，    │    │  │
│  │  │          不构成保本承诺"                               │    │  │
│  │  │   → 系统行为:                                         │    │  │
│  │  │     · 审查结果标记为 human_rejected = true             │    │  │
│  │  │     · 生成一条新案例: verdict=compliant (纠错案例)     │    │  │
│  │  │     · 案例入库，帮助 LLM 在相似场景下做出正确判断       │    │  │
│  │  │     · 纠错案例在后续检索中权重 +20% (高价值案例)       │    │  │
│  │  └──────────────────────────────────────────────────────┘    │  │
│  │                                                               │  │
│  │  ┌──────────────────────────────────────────────────────┐    │  │
│  │  │ ③ 修改 (Modify)                                      │    │  │
│  │  │   "部分同意，但需要调整判定内容"                        │    │  │
│  │  │   → 可修改: 严重程度 / 法条引用 / 修改建议 / 违规理由  │    │  │
│  │  │   → 例: 将 severity 从 critical 降为 major            │    │  │
│  │  │   → 系统行为:                                         │    │  │
│  │  │     · 保存修改后的版本                                 │    │  │
│  │  │     · 生成修正案例: 保留原始 LLM 判定 + 人工修正版     │    │  │
│  │  │     · 两个版本都入库，供系统学习"应该调整的方向"        │    │  │
│  │  └──────────────────────────────────────────────────────┘    │  │
│  │                                                               │  │
│  │  ┌──────────────────────────────────────────────────────┐    │  │
│  │  │ ④ 补充 (Supplement)                                   │    │  │
│  │  │   "LLM 漏检了，这段内容还有其他问题"                   │    │  │
│  │  │   → 人工添加 LLM 未发现的违规项                        │    │  │
│  │  │   → 必填: 违规描述 / 法条引用 / 建议                   │    │  │
│  │  │   → 系统行为:                                         │    │  │
│  │  │     · 生成一条"漏检案例"                               │    │  │
│  │  │     · 标记 source=human_supplement                    │    │  │
│  │  │     · 这是最高价值的案例类型 — 直接指出 LLM 的盲区     │    │  │
│  │  │     · 案例入库后，相似内容的检索优先级提高              │    │  │
│  │  └──────────────────────────────────────────────────────┘    │  │
│  │                                                               │  │
│  └───────────────────────────────────────────────────────────────┘  │
│                                                                      │
│  ┌───────────────────────────────────────────────────────────────┐  │
│  │  通用选项:                                                     │  │
│  │  · 添加复核备注 (自由文本)                                     │  │
│  │  · 关联相似案例 (手动链接)                                     │  │
│  │  · 标记为"典型案例" (加入教学库)                                │  │
│  └───────────────────────────────────────────────────────────────┘  │
└─────────────────────────────────────────────────────────────────────┘
```

## 5.3 案例沉淀流程 — 从反馈到入库

```
┌──────────────────────────────────────────────────────────────────────┐
│  案例沉淀流水线                                                       │
│                                                                      │
│  触发: 人工复核完成(确认/驳回/修改/补充)                               │
│                                                                      │
│  ┌────────────────────────────────────────────────────────────────┐  │
│  │  Step 1: 案例构建                                              │  │
│  │                                                                │  │
│  │  从复核结果中提取:                                              │  │
│  │  · reviewed_content: 被审查的原始内容                           │  │
│  │  · ai_verdict: LLM 的原始判定                                  │  │
│  │  · human_verdict: 人工最终判定                                  │  │
│  │  · human_action: confirmed / rejected / modified / supplemented│  │
│  │  · reason: 违规理由(最终版)                                     │  │
│  │  · law_references: 法条引用(最终版)                             │  │
│  │  · suggestion: 修改建议(最终版)                                 │  │
│  │  · context: 内容类型/产品类型/渠道等元数据                      │  │
│  └────────────────────┬───────────────────────────────────────────┘  │
│                       │                                              │
│                       ▼                                              │
│  ┌────────────────────────────────────────────────────────────────┐  │
│  │  Step 2: 案例质量评估                                          │  │
│  │                                                                │  │
│  │  为每条案例计算"学习价值分":                                    │  │
│  │                                                                │  │
│  │  高价值 (+3):  人工补充的漏检案例(LLM盲区)                      │  │
│  │  高价值 (+2):  人工驳回的案例(LLM误判)                          │  │
│  │  中价值 (+1):  人工修改的案例(LLM部分正确)                      │  │
│  │  标准价值(+0): 人工确认的案例(LLM正确)                          │  │
│  │                                                                │  │
│  │  额外加分:                                                     │  │
│  │  +1: 被标记为"典型案例"                                        │  │
│  │  +1: 涉及新型违规模式(知识库中无相似案例)                       │  │
│  │  +1: 涉及新发布的法规                                          │  │
│  │                                                                │  │
│  │  学习价值分决定:                                                │  │
│  │  · 案例在检索结果中的排序权重                                   │  │
│  │  · 案例是否进入"精选案例库"(高价值优先)                         │  │
│  └────────────────────┬───────────────────────────────────────────┘  │
│                       │                                              │
│                       ▼                                              │
│  ┌────────────────────────────────────────────────────────────────┐  │
│  │  Step 3: 向量化与入库                                          │  │
│  │                                                                │  │
│  │  对案例生成多粒度 Embedding (同 3.3.2)                          │  │
│  │  · 审查内容 Embedding                                          │  │
│  │  · 违规理由 Embedding                                          │  │
│  │  · 组合 Embedding                                              │  │
│  │                                                                │  │
│  │  存入:                                                          │  │
│  │  · PostgreSQL: 案例结构化数据                                   │  │
│  │  · Milvus: 案例向量(用于语义检索)                               │  │
│  │  · Elasticsearch: 案例全文(用于关键词检索)                      │  │
│  └────────────────────┬───────────────────────────────────────────┘  │
│                       │                                              │
│                       ▼                                              │
│  ┌────────────────────────────────────────────────────────────────┐  │
│  │  Step 4: 自动关联                                              │  │
│  │                                                                │  │
│  │  · 检索知识库中相似的案例，建立 related_cases 关联              │  │
│  │  · 如果该案例涉及的法条有新的解读                               │  │
│  │    → 自动标记对应法条知识为"有新案例解读，建议复核"              │  │
│  │  · 如果该案例是"驳回"类型                                      │  │
│  │    → 检查是否有同法条的其他驳回案例                              │  │
│  │    → 如果同法条驳回率 > 30%，触发法条知识复核提醒                │  │
│  └────────────────────────────────────────────────────────────────┘  │
└──────────────────────────────────────────────────────────────────────┘
```

## 5.4 案例如何被使用 — 在审查中的作用

```
下一次审查时:

用户提交: "该基金亏损风险较低"

  → 向量检索案例库:
    命中案例 CASE-2024-00012345:
      原文: "亏损概率很小"
      判定: violation (人工确认)
      理由: 构成暗示保本

    命中案例 CASE-2024-00012400:
      原文: "本基金属于中低风险产品"
      判定: compliant (人工确认)
      理由: 客观描述产品风险等级，不构成保本承诺

  → 两条案例一起放入 LLM 的 prompt:
    LLM 看到:
    - "亏损概率很小" 被判违规
    - "属于中低风险产品" 被判合规
    - 当前要审查: "亏损风险较低"

    LLM 的判断会更精准:
    "亏损风险较低"更接近"亏损概率很小"的表述模式，
    构成对风险的弱化暗示，应判定为违规。
```

## 5.6 复核策略 — 不是所有审查都需要人工复核

```
复核策略配置 (每个租户可自定义):

┌────────────────────────────────────────────────────────────────┐
│  复核模式                                                      │
│                                                                │
│  模式1: 全量复核 (严格模式)                                     │
│    所有审查结果都进入人工复核队列                                │
│    适用: 系统上线初期 / 高合规要求的企业                         │
│                                                                │
│  模式2: 风险驱动复核 (推荐)                                     │
│    高风险 (score > 50): 100% 人工复核                          │
│    中风险 (score 20-50): 50% 抽样复核                          │
│    低风险 (score < 20): 10% 抽样复核                           │
│    法条引用未验证: 100% 人工复核                                │
│                                                                │
│  模式3: 抽样复核 (成熟期)                                      │
│    所有审查结果: 10% 随机抽样复核                               │
│    +: 法条引用未验证的 100% 复核                                │
│    适用: 系统准确率稳定在 95% 以上后                             │
│                                                                │
│  模式切换建议:                                                  │
│    上线第1-3月: 全量复核                                        │
│    准确率 > 90% 后: 切换为风险驱动                              │
│    准确率 > 95% 且稳定 3 个月后: 可切换为抽样复核               │
└────────────────────────────────────────────────────────────────┘
```
