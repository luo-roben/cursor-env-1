## 1. 审查的时候拿什么去审？——完整的数据流转

### 1.1 核心答案

**是的，审的是原文。** 但不是把原文直接扔给 LLM，而是经过"解析→分段→检索上下文→组装 prompt"之后，原文作为 prompt 的一部分送给 LLM。

完整数据流转：

```
用户上传原始内容（一张海报图片）
        │
        ▼
┌─ 阶段2: 内容解析 ──────────────────────────────────────────────┐
│                                                                 │
│  图片 → OCR 提取文字 → 得到纯文本                               │
│                                                                 │
│  OCR 提取结果（这就是"原文"）:                                   │
│  ┌───────────────────────────────────────────────────────────┐ │
│  │ "光伏行业迎来爆发，新能源基金值得关注                        │ │
│  │  XX沪深300ETF联接基金 (代码: 001234)                       │ │
│  │  过去一年涨幅达35%，同类排名前5%                            │ │
│  │  现在买入，亏损概率很小"                                    │ │
│  └───────────────────────────────────────────────────────────┘ │
│                                                                 │
│  然后按语义边界分段 ↓                                            │
│                                                                 │
│  段落1: "光伏行业迎来爆发，新能源基金值得关注"                    │
│  段落2: "XX沪深300ETF联接基金 (代码: 001234)"                    │
│  段落3: "过去一年涨幅达35%，同类排名前5%"                        │
│  段落4: "现在买入，亏损概率很小"                                  │
│                                                                 │
│  + 元数据: {content_type: "营销海报", ...}                       │
└───────────────────────────────────┬─────────────────────────────┘
                                    │
                                    ▼
┌─ 阶段3: 检索上下文 ────────────────────────────────────────────┐
│                                                                 │
│  用这 4 个段落 + 元数据，去知识库检索相关法条和案例               │
│  （详见下面第3节）                                               │
│                                                                 │
│  检索结果: 50条相关法条 + 10条相似案例                            │
└───────────────────────────────────┬─────────────────────────────┘
                                    │
                                    ▼
┌─ 阶段4: 组装 Prompt 给 LLM ───────────────────────────────────┐
│                                                                 │
│  [System Prompt]                                                │
│  你是金融合规审查专家...                                         │
│  === 适用法规 ===                                               │
│  (50条法条的摘要，来自检索结果)                                  │
│  === 参考案例 ===                                               │
│  (10条案例的摘要，来自检索结果)                                  │
│  === 企业规则 ===                                               │
│  (企业自定义规则)                                                │
│                                                                 │
│  [User Prompt]                                                  │
│  请审查以下营销海报内容（公募基金，微信渠道）：                    │
│                                                                 │
│  【段落1】光伏行业迎来爆发，新能源基金值得关注    ← 原文在这里    │
│  【段落2】XX沪深300ETF联接基金 (代码: 001234)    ← 原文在这里    │
│  【段落3】过去一年涨幅达35%，同类排名前5%        ← 原文在这里    │
│  【段落4】现在买入，亏损概率很小                  ← 原文在这里    │
│                                                                 │
└───────────────────────────────────┬─────────────────────────────┘
                                    │
                                    ▼
                          LLM 逐段审查，输出结果
```

**总结：LLM 看到的是原文 + 检索到的法规/案例上下文。原文是审查的对象，法规和案例是审查的依据。**

### 1.2 不同内容类型，"原文"的来源不同

| 用户上传的内容 | "原文"是怎么得到的 | 说明 |
|---|---|---|
| 纯文本（直接粘贴） | 就是用户输入的文字 | 最简单，无需转换 |
| 图片/海报 | OCR 提取出的文字 | 图片本身不送给 LLM，只送提取出的文字 |
| PDF/Word | 文档解析提取出的文字 | 保留章节结构 |
| 视频 | 语音转文字 + 画面 OCR | 两路文字合并 |

> **关键点：不管原始格式是什么，最终送给 LLM 审查的都是纯文本。** 图片中的字号检测、布局分析等由专门的解析器处理，结果作为元数据附带，不直接送给 LLM。

## 2. 内容怎么分段？——分段策略详解

### 2.1 为什么要分段？

分段有两个目的：
1. **检索更精准**：整篇文章做向量检索，会得到一个"平均"语义，丢失具体违规点。分段后每段独立检索，能精确命中该段对应的法条。
2. **审查结果定位到具体位置**：LLM 需要告诉用户"第3段违规"，所以必须有段落编号。

### 2.2 分段规则

分段不是按字数机械切割，而是按**语义边界**切分：

```
分段策略 (按优先级):

1. 如果内容有明确的段落标记（换行符、分段符）
   → 按段落标记切分
   → 每段就是一个自然段落

2. 如果内容是连续文本（如 OCR 提取的海报文字）
   → 按句子边界切分（句号、感叹号、问号）
   → 语义相关的相邻句子合并为一段
   → 每段不超过 200 字

3. 如果内容是结构化文档（PDF/说明书）
   → 按章节/小节切分
   → 每个章节作为一个段落
   → 超过 500 字的章节再按段落/句子进一步切分

4. 如果是极短内容（如一句话的推文）
   → 整条作为一个段落，不切分
```

### 2.3 海报的分段示例

```
OCR 提取的原始文本（没有换行符，是一整坨）:
"光伏行业迎来爆发，新能源基金值得关注XX沪深300ETF联接基金
(代码: 001234)过去一年涨幅达35%，同类排名前5%现在买入，亏损概率很小"

分段器处理过程:

Step 1: 识别语义边界
  → "值得关注" 和 "XX沪深300" 之间是话题转换
  → "001234)" 和 "过去一年" 之间是话题转换
  → "前5%" 和 "现在买入" 之间是话题转换

Step 2: 切分
  段落1: "光伏行业迎来爆发，新能源基金值得关注"       (主题: 行业推荐)
  段落2: "XX沪深300ETF联接基金 (代码: 001234)"       (主题: 产品信息)
  段落3: "过去一年涨幅达35%，同类排名前5%"            (主题: 业绩展示)
  段落4: "现在买入，亏损概率很小"                      (主题: 购买建议)

Step 3: 每段独立进入检索和审查
```

### 2.4 长文档的分段示例

```
基金招募说明书（3万字）:

Step 1: 按章节切分
  章节1: "一、基金管理人" (800字)        → 整章作为一个 chunk
  章节2: "二、基金托管人" (600字)        → 整章作为一个 chunk
  章节3: "三、基金的投资" (3000字)       → 超过500字, 进一步切分
    段落3-1: "投资目标" (200字)
    段落3-2: "投资范围" (400字)
    段落3-3: "投资策略" (800字)
    段落3-4: "投资限制" (600字)
    ...
  章节4: "四、风险揭示" (2000字)         → 进一步切分
    ...
  ...

Step 2: 每个 chunk/段落独立检索和审查
```

## 3. 分段后怎么检索？——不是拿每个字去搜

### 3.1 核心答案

**绝对不是拿每个汉字去搜。** 是拿每个**段落**（通常一句话或一个自然段，10-200字）作为一个整体，去做向量检索。

### 3.2 向量检索的工作原理

```
段落3: "过去一年涨幅达35%，同类排名前5%"
                    │
                    ▼
           Embedding 模型 (bge-large-zh-v1.5)
                    │
                    ▼
           得到一个 1024 维的向量
           [0.023, -0.156, 0.089, ..., 0.045]
           这个向量代表了这段话的"整体语义"
                    │
                    ▼
           拿这个向量去 Milvus 搜索
           找到向量空间中最近的 10 条法条知识
                    │
                    ▼
           命中:
           - 法条A的 violation_example "预期年化收益12%" (相似度 0.87)
             → 因为"涨幅达35%"和"年化收益12%"都在描述基金收益
           - 法条B的 behavior "展示业绩需标注时间区间" (相似度 0.84)
             → 因为"过去一年涨幅"涉及业绩展示
```

**重要：一次向量检索 = 一个段落 → 一个向量 → 搜 Milvus → 返回最相关的 N 条法条。**

如果有 4 个段落，就做 4 次向量检索（可以并行），每次用一个段落的向量去搜。

### 3.3 案例检索也是同理

```
段落4: "现在买入，亏损概率很小"
                    │
                    ▼
           同一个 Embedding 模型
                    │
                    ▼
           得到向量 [0.112, -0.034, ...]
                    │
                    ▼
           拿这个向量去 Milvus 的案例库搜索
           找到最相似的 3 条历史案例
                    │
                    ▼
           命中:
           - 案例#12345 原文: "亏损概率很小"    (相似度 0.95)
             判定: violation, 理由: 暗示保本
           - 案例#12400 原文: "本基金属于中低风险产品" (相似度 0.78)
             判定: compliant, 理由: 客观描述风险等级
```

### 3.4 完整的检索量

```
假设一张海报分成 4 个段落:

向量检索 (路径C — 法条):
  段落1 → 搜 Milvus law_knowledge_vectors → top 10 → 10条法条
  段落2 → 搜 Milvus law_knowledge_vectors → top 10 → 10条法条
  段落3 → 搜 Milvus law_knowledge_vectors → top 10 → 10条法条
  段落4 → 搜 Milvus law_knowledge_vectors → top 10 → 10条法条
  → 40条法条（去重后约 25 条）

向量检索 (路径D — 案例):
  段落1 → 搜 Milvus review_cases_vectors → top 3 → 3条案例
  段落2 → 搜 Milvus review_cases_vectors → top 3 → 3条案例
  段落3 → 搜 Milvus review_cases_vectors → top 3 → 3条案例
  段落4 → 搜 Milvus review_cases_vectors → top 3 → 3条案例
  → 12条案例（去重后约 10 条）

结构化查询 (路径A — 按内容类型):
  content_type = "营销海报" → 搜 PostgreSQL → ~15 条法条

结构化查询 (路径B — 按产品类型):
  product_type = "公募基金" → 搜 PostgreSQL → ~20 条法条

直接加载 (路径E — 企业规则):
  tenant_id = "xxx" → 搜 PostgreSQL → ~5 条规则

→ 合并去重 → 约 50 条法条 + 10 条案例 + 5 条规则
→ Token 预算控制 → 最终上下文
```

## 4. 元数据到底是什么？

### 4.1 元数据的定义

元数据是**描述内容本身特征的结构化信息**，不是内容的文字本身。它由内容解析阶段自动提取 + 用户手动选择共同构成。

### 4.2 完整的元数据结构

```json
{
  "content_type": "营销海报",
  "product_type": "公募基金",
  "product_code": "001234",
  "channel": "微信朋友圈",
  "file_type": "image/jpeg",
  "file_size_bytes": 2048576,
  "upload_time": "2024-03-15T14:30:00Z",
  "submitter_id": "user-zhangsan",
  "tenant_id": "tenant-fund-company-a",

  "parse_info": {
    "ocr_engine": "PaddleOCR",
    "ocr_confidence": 0.95,
    "detected_language": "zh-CN",
    "total_text_length": 128,
    "segment_count": 4,
    "has_image_elements": true,
    "detected_font_sizes": [48, 24, 12, 8],
    "risk_warning_font_size": 8,
    "max_content_font_size": 48,
    "layout_regions": [
      {"type": "title", "text": "光伏行业迎来爆发...", "font_size": 48, "position": "top"},
      {"type": "body", "text": "过去一年涨幅...", "font_size": 24, "position": "center"},
      {"type": "disclaimer", "text": "(如有的话)", "font_size": 8, "position": "bottom"}
    ]
  }
}
```

### 4.3 元数据字段说明

| 字段 | 来源 | 说明 | 用途 |
|------|------|------|------|
| `content_type` | 用户选择 / 系统自动识别 | 内容形式分类，如"营销海报"、"微信推文" | 检索路径A（按内容类型查法条） |
| `product_type` | 用户选择 | 金融产品类型，如"公募基金"、"私募基金" | 检索路径B（按产品类型查法条） |
| `product_code` | 用户输入 / OCR 自动识别 | 产品代码，如基金代码 001234 | 自动关联企业产品库中的详细信息 |
| `channel` | 用户选择 | 发布渠道，如"微信朋友圈"、"官网" | 影响适用的法规范围 |
| `file_type` | 系统自动识别 | 文件 MIME 类型 | 决定使用哪个解析器 |
| `file_size_bytes` | 系统自动识别 | 文件大小 | 格式校验 |
| `parse_info.*` | 解析器自动生成 | 解析过程产生的附加信息 | 完整性检查、图片特有的字号检查 |
| `parse_info.risk_warning_font_size` | OCR + 布局分析 | 风险提示文字的字号 | 检查是否满足"不小于最大字号1/2"的法定要求 |
| `parse_info.layout_regions` | OCR + 布局分析 | 图片中各区域的文字和位置 | 检查风险提示位置是否醒目 |

**元数据不送给 LLM 审查（除了 content_type/product_type/channel）。** `parse_info` 中的字号、布局信息由专门的完整性检查器 (CompletenessChecker) 使用，不进入 LLM prompt。

## 5. 内容类型和产品类型的分类体系

### 5.1 核心答案

**这些分类是人为定义的，但不是你手动维护的——系统内置一套基础分类，LLM 解析法条时会自动扩展，你也可以随时增删。**

### 5.2 这些分类到底分的是什么？

这是两套独立的分类体系，分别标注在法条和审查内容上：

```
分类体系的作用:

                    法条知识                        审查内容
                    ────────                        ────────
内容类型标签:       第24条.applicable_content_types   用户上传时选择的 content_type
                    = ["营销海报", "微信推文", ...]    = "营销海报"

产品类型标签:       第24条.applicable_product_types   用户上传时选择的 product_type
                    = ["公募基金", "ETF", ...]        = "公募基金"

                          ↓                              ↓
                    检索时做匹配: WHERE '营销海报' = ANY(applicable_content_types)
                    → 找到所有标注了"适用于营销海报"的法条
```

**法条侧**：每条法条被标注了"适用于哪些内容类型"和"适用于哪些产品类型"。这个标注是 LLM 解析法条时自动生成的，人工确认时可以修改。

**审查内容侧**：用户上传内容时选择（或系统自动识别）内容类型和产品类型。

**匹配逻辑**：审查时，系统用审查内容的类型去法条的标签里做精确查询。

### 5.3 内容类型分类 (content_type)

这是描述"宣传物料的形式"的分类。由系统内置 + LLM 解析时自动发现 + 人工手动添加：

| 大类 | 具体类型 | 说明 |
|------|---------|------|
| **图片类** | 营销海报 | 单张图片，含产品宣传文字 |
|  | 宣传长图 | 多屏长图，通常用于朋友圈 |
|  | 产品卡片 | 产品要素展示卡 |
| **文档类** | 基金招募说明书 | 法定披露文件 |
|  | 基金合同 | 法律合同文件 |
|  | 产品说明书 | 产品要素说明 |
|  | 投资者教育材料 | 投教内容 |
| **文本类** | 微信推文 | 公众号/朋友圈图文 |
|  | 短信文案 | 营销短信 |
|  | APP推送文案 | APP push 通知文字 |
|  | 直播话术脚本 | 直播前准备的文稿 |
| **多媒体类** | 短视频 | 抖音/快手等短视频 |
|  | 直播录像 | 直播回放 |
|  | H5页面 | 移动端营销页 |
| **路演类** | 路演PPT | 路演幻灯片 |
|  | 路演纪要 | 路演文字记录 |

> **这个列表不是固定的。** 存在 PostgreSQL 的一个配置表中，可以随时添加新类型。LLM 解析新法规时如果发现了新的适用内容类型（比如"播客音频"），也会自动建议添加。

### 5.4 产品类型分类 (product_type)

这是描述"金融产品类别"的分类。主要由行业标准和法规定义决定：

| 大类 | 具体类型 | 适用的主要法规 |
|------|---------|-------------|
| **公募基金** | 股票型基金 | 基金销售管理办法、基金法 |
|  | 债券型基金 | |
|  | 混合型基金 | |
|  | 货币市场基金 | |
|  | 指数基金/ETF | |
|  | LOF/QDII/FOF | |
| **私募基金** | 私募股权基金 | 私募基金监管条例 |
|  | 私募证券基金 | |
| **银行理财** | 固定收益类 | 理财产品销售管理办法 |
|  | 权益类 | |
|  | 混合类 | |
| **保险产品** | 人寿保险 | 保险法、互联网保险业务监管办法 |
|  | 健康保险 | |
|  | 财产保险 | |
| **信托产品** | 集合信托 | 信托公司管理办法 |
| **通用** | (不限特定产品) | 广告法、反不正当竞争法 |

### 5.5 分类是谁定义的？怎么维护？

```
分类的生命周期:

┌─────────────────────────────────────────────────────────────┐
│  初始化:                                                     │
│  系统上线时，内置一套基础分类（上面两个表的内容）                │
│  存在 PostgreSQL 的 content_types / product_types 配置表      │
│                                                              │
│  自动扩展:                                                    │
│  当 LLM 解析新法条时，如果发现法条提到了新的内容类型或产品类型   │
│  （比如法条里写"互联网保险自营网络平台"，这是一个新内容类型）    │
│  LLM 会在 applicable_content_types 里输出这个新类型              │
│  → 人工确认时看到 → 决定是否添加到系统分类中                    │
│                                                              │
│  人工添加:                                                    │
│  系统管理员可以通过管理后台添加/修改/合并分类                    │
│  比如把"朋友圈图文"和"微信推文"合并为一个分类                   │
│                                                              │
│  租户自定义:                                                  │
│  企业可以添加自己的内容类型（比如"内部早报"、"客户月报"）         │
│  这些类型只对该租户可见                                        │
└─────────────────────────────────────────────────────────────┘
```

### 5.6 法条分类和审查内容分类是对应的吗？

**是同一套分类体系。** 法条侧用 `applicable_content_types` 标注"这条法规适用于哪些内容类型"，审查内容侧用 `content_type` 标注"这个内容是什么类型"。两边用的是同一个分类词表。

```
同一个分类词表:

  分类词表: ["营销海报", "微信推文", "基金招募说明书", ...]
                │                              │
                ▼                              ▼
  法条侧:                               审查内容侧:
  第24条.applicable_content_types        用户选择 content_type
  = ["营销海报", "微信推文", ...]         = "营销海报"
                │                              │
                └──────── 匹配 ────────────────┘
                WHERE '营销海报' = ANY(applicable_content_types)
```

产品类型同理。

## 6. law_knowledge 表存什么？数据从哪来？

### 6.1 law_knowledge 存的是什么？

`law_knowledge`（在数据模型中叫 `law_articles`）存的是**经过 LLM 解析 + 人工确认后的结构化法条知识**。不是法律原文的简单复制，而是解析后的知识条目。

**每一行 = 一条法律条文的结构化知识**

### 6.2 一条数据长什么样？

以《基金销售管理办法》第24条第1款第1项为例，数据库中存储的一行：

| 字段 | 值 | 说明 |
|------|---|------|
| id | 1001 | 自增主键 |
| source_id | "csrc-2020-fund-sales" | 来自哪部法规 |
| law_name | "公开募集证券投资基金销售机构监督管理办法" | 法律全称 |
| article_id | "第24条第1款第1项" | 条款编号 |
| original_text | "基金销售机构及其从业人员从事基金销售业务，不得以预期收益率、预计收益等方式宣传、介绍基金产品" | **法条原文（直接复制，一字不改）** |
| norm_type | "禁止" | LLM 判断出的规范类型 |
| subject | ["基金销售机构", "基金销售从业人员"] | LLM 提取的约束主体 |
| behavior | "以预期收益率、预计收益等方式宣传、介绍基金产品" | LLM 提取的被禁止行为 |
| applicable_content_types | ["营销海报", "宣传物料", "微信推文", "直播话术", "基金推介材料"] | LLM 判断 + 人工确认：这条法律适用于哪些内容类型 |
| applicable_product_types | ["公募基金", "ETF", "LOF", "指数基金", ...] | LLM 判断 + 人工确认：适用于哪些产品 |
| key_phrases | ["预期收益率", "预计收益", "宣传", "介绍"] | LLM 提取的关键词 → 用于 ES 关键词检索 |
| violation_examples | ["预期年化收益12%", "预计明年达到15%的回报", "有望获得20%以上收益"] | LLM 生成的违规示例 → **向量化后存 Milvus，审查时用待审内容去匹配** |
| compliant_examples | ["该基金过去三年年化收益率为8.5%（截至...，过往业绩不代表未来表现）"] | LLM 生成的合规示例 → 帮助区分边界 |
| semantic_extensions | ["暗示未来收益的具体数值", "使用历史收益暗示未来表现"] | LLM 生成的语义延伸 → 向量化后存 Milvus |
| status | "published" | 已经过人工确认 |

### 6.3 数据从哪来？

```
数据来源链路:

  法律原文 (证监会官网/北大法宝)
      │
      ▼
  爬虫采集 → 存入 law_sources 表（原文）
      │
      ▼
  LLM 按"条-款-项"拆分 → 得到一条条独立法条
      │
      ▼
  LLM 对每条法条做结构化解析
  → 提取 norm_type, subject, behavior, applicable_*类型, key_phrases, 违规示例 等
      │
      ▼
  进入人工确认队列 → 合规人员审核
  → 确认/修改 → status 变为 "published"
      │
      ▼
  发布后自动触发:
  → original_text 做 Embedding → 存入 Milvus (law_knowledge_vectors)
  → violation_examples 每条做 Embedding → 存入 Milvus
  → semantic_extensions 每条做 Embedding → 存入 Milvus
  → key_phrases 写入 Elasticsearch 索引
  → 实体关系写入 Neo4j 知识图谱
```

### 6.4 数据准确吗？

法条原文 (`original_text`) 是直接从法律文本复制的，**100% 准确**。

LLM 生成的结构化字段（`applicable_content_types`、`violation_examples` 等）是 LLM 的解读，**可能有误**。所以必须经过人工确认这一步。人工确认是质量关卡：

- 合规人员逐条检查 LLM 的解析结果
- 确认正确的 → 发布
- 发现错误的 → 修改后发布，或退回重新解析
- 发布后进入知识库 → 审查时可被检索到

**总结：original_text 100% 准确（原文复制），结构化字段经过 LLM 生成 + 人工确认，准确率取决于人工确认的质量。**

## 7. 五路检索的本质——不全是向量检索

### 7.1 五路检索各用的是什么技术？

| 路径 | 检索方式 | 用的什么数据库 | 是向量检索吗？ |
|------|---------|-------------|-------------|
| **A: 按内容类型** | SQL 精确查询 | PostgreSQL | **不是**，是普通 SQL WHERE 查询 |
| **B: 按产品类型** | SQL 精确查询 | PostgreSQL | **不是**，是普通 SQL WHERE 查询 |
| **C: 按内容语义** | 向量相似度搜索 | Milvus | **是** |
| **D: 按案例相似** | 向量相似度搜索 | Milvus | **是** |
| **E: 企业规则** | SQL 精确查询 | PostgreSQL | **不是**，是普通 SQL WHERE 查询 |

**只有路径 C 和 D 是向量检索。路径 A、B、E 是普通的数据库查询。**

### 7.2 为什么不全用向量检索？

```
路径A的查询:
SELECT * FROM law_articles
WHERE '营销海报' = ANY(applicable_content_types)
AND status = 'published';

这个查询的意思是：
"找出所有标注了'适用于营销海报'的法条"

为什么不用向量检索做这件事？
因为这是一个确定性的问题——法条要么标注了"适用于营销海报"，要么没标注。
没有"可能适用""也许适用"的中间状态。
普通 SQL 查询又快又准，不需要向量检索。

向量检索适合的场景是：
"这段话是否违反了某条法规？"
→ 这是一个语义理解问题，用向量检索合适
```

### 7.3 law_knowledge 表的角色

`law_knowledge` (law_articles) 表在五路检索中的参与方式：

```
law_articles 表 (PostgreSQL)
├── 路径A: SELECT ... WHERE content_type = ANY(applicable_content_types)
├── 路径B: SELECT ... WHERE product_type = ANY(applicable_product_types)
└── 路径C/D 的源数据也来自这张表:
    law_articles 发布时 → 向量化 → 存入 Milvus
    路径C 在 Milvus 中搜 → 搜到的结果通过 article_id 关联回 law_articles
```

## 8. 完整审查流程逐步走一遍

用一个完整的端到端例子串联以上所有概念。

### 场景

用户上传一张基金营销海报图片，选择产品类型"公募基金"，渠道"微信朋友圈"。

### Step 1: 快速过滤 (< 10ms)

```
输入: 图片文件 + 元数据 {product_type: "公募基金", channel: "微信朋友圈"}

检查:
  ✓ 文件格式: image/jpeg，支持
  ✓ 文件大小: 2MB，不超限
  ✓ (禁用词检查需要文字，先跳过，等 OCR 之后再做)

输出: 通过，继续
```

### Step 2: 内容解析 (~1.5s)

```
输入: 海报图片

处理:
  1. PaddleOCR 识别图片中的文字
  2. 布局分析：识别标题区/正文区/免责区
  3. 字号检测：最大字号 48px，最小字号 8px

输出:
  段落列表:
    段落1: "光伏行业迎来爆发，新能源基金值得关注"
    段落2: "XX沪深300ETF联接基金 (代码: 001234)"
    段落3: "过去一年涨幅达35%，同类排名前5%"
    段落4: "现在买入，亏损概率很小"

  元数据:
    content_type: "营销海报" (系统识别出是图片类→海报)
    parse_info: {
      risk_warning_font_size: null,  (没发现风险提示文字!)
      max_content_font_size: 48,
      segment_count: 4,
      ...
    }

然后对 OCR 文本做禁用词检查:
  租户禁用词表: ["躺赚", "暴涨", "无脑定投", ...]
  检查: 4个段落中未命中禁用词 → 跳过
```

### Step 3: ACE 上下文组装 (~400ms, 5路并行)

```
路径A — 按内容类型 (PostgreSQL, ~50ms):
  SELECT * FROM law_articles
  WHERE '营销海报' = ANY(applicable_content_types)
  AND status = 'published';
  → 命中 15 条法条 (海报格式要求、字号要求、必备元素等)

路径B — 按产品类型 (PostgreSQL, ~50ms):
  SELECT * FROM law_articles
  WHERE '公募基金' = ANY(applicable_product_types)
  AND status = 'published';
  → 命中 20 条法条 (公募基金销售规范等)

路径C — 按语义检索法条 (Milvus, ~200ms):
  段落1 向量 → Milvus top10 → 10条法条
  段落2 向量 → Milvus top10 → 6条法条 (产品信息段，法条较少)
  段落3 向量 → Milvus top10 → 10条法条
  段落4 向量 → Milvus top10 → 10条法条
  → 去重后 25 条法条

路径D — 检索相似案例 (Milvus, ~200ms):
  段落1 向量 → Milvus top3 → 3条案例
  段落2 向量 → Milvus top3 → 2条案例
  段落3 向量 → Milvus top3 → 3条案例
  段落4 向量 → Milvus top3 → 3条案例
  → 去重后 10 条案例

路径E — 企业规则 (PostgreSQL, ~30ms):
  SELECT * FROM tenant_custom_rules
  WHERE tenant_id = 'tenant-fund-company-a' AND enabled = true;
  → 5 条规则

合并去重:
  15 + 20 + 25 = 60 条法条 → 去重后 ~50 条
  Token 预算: 法条最多 6000 tokens → 保留相关度最高的 ~40 条
  案例: 10 条 → ~800 tokens
  规则: 5 条 → ~300 tokens
```

### Step 4: Prompt 组装 + LLM 调用 (~8s)

```
组装完成的 Prompt:

[System]
你是金融合规审查专家...

=== 适用法规 ===
1. 《基金销售管理办法》第24条第1款第1项: "不得以预期收益率...宣传"
   违规示例: "预期年化收益12%", "预计明年达到15%"
2. 《基金销售管理办法》第24条第1款第2项: "不得以保本...方式宣传"
   违规示例: "保本理财", "亏损概率极低"
3. 《基金销售管理办法》第25条: "引用基金业绩数据时，应当注明数据来源..."
... (共约40条法条摘要)

=== 参考案例 ===
1. 案例#12345: "亏损概率很小" → 违规(暗示保本) | 第24条第1款第2项
2. 案例#12400: "本基金属于中低风险产品" → 合规(客观描述风险等级)
... (共10条案例)

=== 企业特殊要求 ===
1. 所有营销内容展示收益时必须同时展示业绩比较基准
...

[User]
请审查以下营销海报内容（公募基金，微信朋友圈渠道）：

【段落1】光伏行业迎来爆发，新能源基金值得关注
【段落2】XX沪深300ETF联接基金 (代码: 001234)
【段落3】过去一年涨幅达35%，同类排名前5%
【段落4】现在买入，亏损概率很小
【整体】未发现风险提示文字

→ 调用 GPT-4o → 返回结构化 JSON
```

### Step 5: 后处理 (~100ms)

```
LLM 返回的审查结果:
  段落1: needs_review (可能构成诱导推荐, minor)
  段落3: violation (业绩缺截止日期/来源/基准, major)
  段落4: violation (暗示保本, critical)
  整体: 缺少风险提示声明

后处理:
  1. 法条引用校验:
     - 第24条第1款第2项 → 查知识库 → ✅ 存在
     - 第25条第1款 → 查知识库 → ✅ 存在
     - 第24条第1款第5项 → 查知识库 → ⚠️ 只有第24条第1款第1-4项 → 修正

  2. 风险评分:
     critical(+30) + major(+20) + minor(+10) + 缺失元素(+25) = 85
     risk_level = high

  3. 生成审查报告
```

### Step 6: 返回结果

```
返回给用户:
  风险评分: 85/100 (高风险 🔴)
  发现 3 条违规 + 1 条缺失项
  每条附：违规原文、法条引用、修改建议

同时:
  → 进入人工复核队列 (高风险, P1优先级)
```

## 附: 关键认知总结

| 问题 | 答案 |
|------|------|
| 审查拿什么去审？ | 拿原文（经过 OCR/解析后的纯文本），分段后作为 prompt 的一部分送给 LLM |
| 是拿每个字去向量检索吗？ | 不是。是拿每个**段落**（10-200字）作为整体做一次向量检索 |
| 内容类型/产品类型是通用分类吗？ | 是系统内置 + LLM自动扩展 + 人工可添加的统一分类词表，法条和审查内容共用同一套 |
| 向量检索的单位是什么？ | 一个段落 → 一个向量 → 一次 Milvus 搜索 → 返回 top-N 结果 |
| 元数据是什么？ | 描述内容特征的结构化信息（内容类型、产品类型、渠道、文件信息、OCR解析信息等） |
| law_knowledge 存什么？ | 经过 LLM 解析 + 人工确认的结构化法条知识（原文 + 语义分析 + 违规示例 + 适用范围标签） |
| 五路检索都是向量检索吗？ | 不是。只有路径C和D是向量检索，路径A/B/E是普通SQL查询 |
| 数据准确吗？ | 法条原文100%准确（复制的），结构化字段经LLM生成+人工确认，准确率取决于确认质量 |
