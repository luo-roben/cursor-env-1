# 内容路由、差异化处理与审查后处理

> 本文档聚焦审查执行层中的三个关键环节：如何将不同类型的内容路由到正确的解析和检索流程，如何对各类内容做差异化处理，以及如何对 LLM 审查结果进行后处理（含防幻觉机制）。

---

## 1. 内容路由核心思路

### 1.1 语义驱动检索 vs 标签路由

传统合规系统的核心瓶颈是**标签路由**——需要人工维护一张「内容类型 → 规则集」的映射表。每新增一种内容类型或一条法规，就需要人工决定"这条规则应该适用于哪些内容类型"，然后手动绑定标签。这种方式在法规数量上百、内容类型十几种之后，维护成本呈笛卡尔积式爆炸。

本系统采用**语义驱动检索**的核心理念：

> **法条检索不依赖预设的「内容类型 → 规则集」映射，内容的语义本身决定了检索到哪些法条。**

举例说明：
- 海报里写了"收益率 20%" → 向量搜索自然命中第 24 条（不得以预期收益率宣传）
- 说明书里缺少"风险揭示章节" → 向量搜索命中信息披露法条
- 物料里写了"最好的基金" → 向量搜索命中广告法第 9 条（极限词禁令）

不管内容被分类为"海报"还是"推文"还是"直播话术"，只要它的文字语义与某条法规的违规模式相似，就会被检索到。

### 1.2 混合检索策略：不仅仅靠向量

**重要澄清：系统并非仅依赖向量相似度做检索。** 实际的内容路由采用三路混合检索策略，各有分工：

| 检索方式 | 引擎 | 匹配逻辑 | 核心优势 |
|----------|------|----------|----------|
| **语义向量检索** | Milvus | 对内容段落做 Embedding，与法条知识的多粒度向量做相似度匹配 | 处理**含义层面**的匹配，能捕获语义变体（如"亏损概率低"≈"保本"） |
| **结构化字段查询** | PostgreSQL | 对 `content_type`、`product_type` 等字段做精确匹配（`WHERE 'content_type' IN applicable_content_types`） | 提供**确定性、保证命中**的结果——只要法条标注了适用于"营销海报"，就一定会被检索到，不存在"向量距离不够近就漏掉"的风险 |
| **关键词全文检索** | Elasticsearch | 对法条原文、关键短语做全文搜索 | 捕获**精确术语匹配**——当内容中出现"预期收益率"这样的法定用语时，即使向量距离不是最高的，ES 也能精准命中含有该术语的法条 |

三路检索的结果合并去重后，共同构成 LLM 审查的法规上下文。这种设计确保了：

1. **语义向量检索** 负责"意思相近"的模糊匹配——这是最灵活的一路，能发现人类预想不到的关联
2. **结构化字段查询** 负责"类型确定"的刚性匹配——确保某类内容一定会加载该类型必须遵守的法规，不遗漏
3. **关键词检索** 负责"原词命中"的精确匹配——当内容恰好使用了法条原文中的关键词时，这一路的召回最可靠

### 1.3 路由的实质

因此，"内容路由"在本系统中不是指把内容分发到某个固定的规则集——而是指**根据内容的类型元数据、产品元数据和语义内容，通过混合检索动态找到与之相关的所有法条知识**。这就是 ACE（Agentic Context Engineering）架构的核心思想。

```
内容路由的本质：

  传统方案:  内容 → 类型标签 → 预设规则集 → 审查
                      ↑ 人工维护，易遗漏

  本系统:    内容 → ┬── 结构化字段查询 (类型/产品) ── 确定性命中
                    ├── 语义向量检索 (内容文本)     ── 模糊语义匹配
                    └── 关键词全文检索 (术语)       ── 精确词汇命中
                                 │
                                 ▼
                          合并去重 → 动态上下文 → LLM 审查
```

## 2. 内容解析器工厂 (ContentParserFactory)

虽然法条检索是语义驱动的，但**内容解析**（把原始文件转化为可审查的文本）必须按内容类型差异化处理。一张图片和一份 PDF 的解析方式完全不同。

`ContentParserFactory` 根据文件的 MIME 类型、扩展名和内容特征，选择合适的解析器，最终输出统一的内容表示。

```
┌────────────────────────────────────────────────────────────────────┐
│  ContentParserFactory — 按内容类型选择解析器                        │
│                                                                    │
│  ┌──────────┐                                                     │

│  └─────┬────┘                                                     │
│        │                                                           │
│        ▼                                                           │
│  ┌───────────────┐                                                │
│  │ MIME 类型识别   │                                                │
│  │ + 文件扩展名   │                                                │
│  │ + 内容特征     │                                                │
│  └───────┬───────┘                                                │
│          │                                                         │
│    ┌─────┼─────────────┬─────────────────┬──────────────┐         │
│    ▼     ▼             ▼                 ▼              ▼         │
│  图片   PDF/Word     纯文本/HTML       音频           视频         │

└────────────────────────────────────────────────────────────────────┘
```

### 关键设计点

1. **所有解析器的输出统一为 `UnifiedContent`**——下游的 ACE 上下文组装器和 LLM 审查流程不需要关心原始内容是图片还是 PDF，只处理统一的分段文本。

2. **解析器是可扩展的**——新增内容类型时，只需实现一个新的解析器并注册到工厂，不需要修改下游流程。

3. **解析器不做合规判断**——它只负责把原始文件转化为结构化文本。合规判断全部交给 LLM。

## 3. 各内容类型的差异化处理

不同内容类型在解析方式和特有检查维度上存在显著差异：

| 内容类型 | 解析方式 | 特有检查维度 | 法定要求示例 |
|----------|----------|-------------|-------------|
| **图片/海报** | OCR + 布局分析（字号检测、位置识别） | 风险提示字号是否足够大？位置是否醒目？ | 风险提示文字不得小于最大字号的 1/2 |
| **PDF/说明书** | 文档结构解析 + 目录提取 + 章节拆分 | 法定必备章节是否齐全？目录完整性？ | 基金招募说明书必须包含"风险揭示"独立章节 |
| **纯文本/推文** | 直接分段 | 是否包含风险提示语？字数是否超限？ | 微信推文需包含免责声明 |
| **视频/直播** | 关键帧 OCR + 语音转写 (ASR) | 口头表述合规性、字幕内容、画面中的文字 | 直播中不得口头承诺收益 |
| **H5/网页** | HTML 解析 + 截图 + 链接追踪 | 页面跳转是否合规？弹窗内容？ | 基金购买页面必须展示风险等级匹配提示 |

### 差异化处理的分工

需要明确的是，差异化处理分为两部分：

1. **解析方式的差异化**（由 `ContentParserFactory` 处理）：不同类型用不同的技术手段提取文本。
2. **检查维度的差异化**（由完整性检查器 + LLM 共同处理）：不同类型有不同的法定必备元素和格式要求。

其中，法条内容本身的匹配仍然走语义驱动 + 结构化字段查询 + 关键词检索的混合策略（见第 1 节），不需要为每种内容类型手动维护规则映射。

## 4. 完整性检查器 (CompletenessChecker)

除了逐段文本的合规审查，还需要从整体层面检查内容是否包含法定必备元素。这是 `CompletenessChecker` 的职责。

```
┌─────────────────────────────────────────────────────────────────┐
│  CompletenessChecker                                             │
│                                                                  │
│  输入: UnifiedContent + ContentType + ProductType                │
│                                                                  │
│  检查逻辑 (按内容类型 + 产品类型分支):                             │
│                                                                  │
│  if (content_type == "营销海报" && product_type == "公募基金"):   │
│    必备元素 = [                                                   │
│      "基金全称或简称",                                            │
│      "基金代码",                                                  │
│      "基金管理人名称",                                            │
│      "风险提示语",                                                │
│      "过往业绩不代表未来表现(如展示了业绩)",                       │
│      "数据来源和截止日期(如引用了数据)"                            │
│    ]                                                             │
│    对每个必备元素 → 检查内容是否包含(模糊匹配/语义匹配)            │
│    缺失的元素 → 加入 missing_elements 列表                       │
│                                                                  │
│  if (content_type == "招募说明书"):                               │
│    必备章节 = [                                                   │
│      "基金管理人",                                                │
│      "基金托管人",                                                │
│      "风险揭示",                                                  │
│      "基金的投资",                                                │
│      "基金的收益与分配",                                          │
│      "费用与税收",                                                │
│      ...                                                         │
│    ]                                                             │
│    对每个必备章节 → 检查文档目录/章节标题是否包含                   │
│                                                                  │
│  输出: missing_elements 列表, 每条包含:                           │
│    · element: 缺失的元素名称                                     │
│    · requirement: 法定要求描述                                    │
│    · law_reference: 对应的法条引用                                │
│    · suggestion: 补充建议                                        │
└─────────────────────────────────────────────────────────────────┘
```

### 必备元素清单的来源——动态而非硬编码

**关键设计：必备元素清单存储在知识库中，不是硬编码在代码里。**

上面伪代码中的 `必备元素 = [...]` 列表，实际运行时是从知识库中动态加载的。具体来说：

- 在知识构建层，LLM 解析法规时会识别出"X 类型内容必须包含 Y 元素"这类规范要求，并结构化存储
- `CompletenessChecker` 在运行时通过结构化查询获取当前 `content_type + product_type` 对应的必备元素列表
- 当新法规发布并要求新增某个必备元素时，只需在知识库中更新，不需要修改代码

这使得系统能够**跟随法规变化自动更新完整性检查标准**，无需发版上线。

## 5. 审查结果后处理

LLM 返回审查结果后，系统不会直接输出给用户。需要经过一系列后处理步骤，确保结果的准确性、可解释性和可操作性。

后处理流程包含三个核心环节：

```
LLM 原始输出 → 法条引用校验 → 风险评分计算 → 审查报告生成 → 最终结果
                    ↓                ↓                ↓
                防幻觉机制      量化风险等级      可读报告输出
```

### 5.1 法条引用校验器 (CitationVerifier)

LLM 审查最大的风险是**编造不存在的法条**（即"幻觉"）。例如，LLM 可能引用一个根本不存在的"第 37 条第 2 款"，或者将法条内容张冠李戴。`CitationVerifier` 的职责就是逐一校验 LLM 返回的每条法条引用是否真实存在。

#### 三步校验流程

```
LLM 返回的每条法条引用
          │
          ▼
┌──────────────────────────────────────────────────────────────┐
│  CitationVerifier                                             │
│                                                               │
│  Step 1: 精确匹配                                             │
│    查询知识库:                                                 │
│    SELECT * FROM law_articles                                 │
│    WHERE article_id = :llm_cited_article_id                   │
│    AND law_name LIKE :llm_cited_law_name                      │
│                                                               │
│    如果命中 → 校验通过 ✅                                      │
│    如果未命中 → 进入 Step 2                                   │
│                                                               │
│  Step 2: 模糊匹配                                             │
│    可能 LLM 用了简称或略有不同的编号:                           │
│    例: LLM 说 "第24条第3款" 但实际只有第1款                    │
│                                                               │
│    查询:                                                      │
│    SELECT * FROM law_articles                                 │
│    WHERE law_name LIKE :fuzzy_law_name                        │
│    AND article_id LIKE '第24条%'                              │
│                                                               │
│    如果找到相似法条 → 替换引用并标记 "引用已修正" ⚠️            │
│    如果完全找不到 → 进入 Step 3                                │
│                                                               │
│  Step 3: 幻觉标记                                             │
│    该引用标记为 "无法验证的引用" ❌                             │
│    在审查结果中:                                               │
│    - 保留 LLM 的违规判断和理由                                 │
│    - 法条引用标记为 "未经验证，需人工确认"                      │
│    - 提升该条目的人工复核优先级                                │
│                                                               │
│  输出: 校验后的法条引用列表，每条附状态:                        │
│    verified / corrected / unverified                          │
└──────────────────────────────────────────────────────────────┘
```

#### 各步骤详细说明

**Step 1 — 精确匹配：** 这是最直接的校验。系统用 LLM 输出的法律名称和条款编号在知识库中做精确查询。如果法条编号和法律名称都能精确匹配到知识库中的一条记录，则校验通过，标记为 `verified`。这说明 LLM 引用了一条确实存在的法条。

**Step 2 — 模糊匹配：** 当精确匹配失败时，不能立即判定为幻觉——LLM 经常会犯一些"小错"，例如：
- 使用法律简称而非全称（如"基金销售办法"而非"公开募集证券投资基金销售机构监督管理办法"）
- 条款编号略有偏差（如把"第 24 条第 1 款第 2 项"说成"第 24 条第 3 款"）
- 遗漏款项层级（如只说"第 24 条"但实际应该是"第 24 条第 1 款"）

模糊匹配通过放宽查询条件（法律名称用 LIKE，条款编号匹配到"条"这一级），尝试找到最接近的真实法条。如果找到了，就自动用正确的法条替换 LLM 的引用，并标记为 `corrected`。审查报告中会显示"引用已修正"提示，让复核人员知道这条引用经过了系统纠正。

**Step 3 — 幻觉标记：** 当精确匹配和模糊匹配都无法找到对应法条时，该引用被判定为高度可疑的幻觉，标记为 `unverified`。此时系统的处理策略是：
- **不删除该条审查结论**——LLM 的违规判断本身可能是正确的，只是引用了错误的法条
- **将法条引用标记为"未经验证，需人工确认"**——在报告中醒目提示
- **自动提升该审查条目的人工复核优先级至 P0**——确保人工优先处理这类不确定的结果

#### 校验结果对后续流程的影响

| 校验状态 | 标记 | 对风险评分的影响 | 对人工复核的影响 |
|----------|------|-----------------|-----------------|
| `verified` ✅ | 引用已验证 | 得分权重 × 1.0（全额计算） | 正常优先级 |
| `corrected` ⚠️ | 引用已修正 | 得分权重 × 0.8（略降） | 优先级适度提升 |
| `unverified` ❌ | 未经验证 | 得分权重 × 0.5（大幅降低） | 优先级提升至 P0（最高） |

这一设计使得系统在面对 LLM 幻觉时能够"优雅降级"——不会因为一条幻觉引用就丢失有价值的审查结论，同时通过降低权重和提升人工复核优先级来控制风险。

### 5.2 风险评分计算

风险评分是对审查结果的量化总结，帮助复核人员快速判断紧急程度。

**重要说明：风险评分存在两个层级——问题级别（Issue Level）和任务级别（Task Level）。**

#### 5.2.1 问题级别评分

每个被发现的问题（issue）本身有一个严重程度（severity），对应一个固定分值：

| 严重程度 | 含义 | 分值 | 示例 |
|----------|------|------|------|
| `critical` | 严重违规 | **+30** | 保本承诺、虚假陈述 |
| `major` | 重要违规 | **+20** | 业绩数据缺失截止日期、来源 |
| `minor` | 轻微违规 | **+10** | 措辞不当、诱导性表述 |
| `info` | 建议优化 | **+5** | 可优化的表述、非强制性建议 |

此外，缺失必备元素也会产生分值：

| 缺失类型 | 分值 |
|----------|------|
| 缺失 `critical` 级必备元素 | **+25** |
| 缺失 `recommended` 级必备元素 | **+10** |

#### 5.2.2 加权因子

每条问题的分值还会根据其法条引用的校验状态做加权：

| 引用校验状态 | 加权因子 | 说明 |
|-------------|---------|------|
| `verified` | × 1.0 | 法条引用已验证，分值全额计算 |
| `corrected` | × 0.8 | 法条引用经修正，分值略降 |
| `unverified` | × 0.5 | 法条引用未验证，分值大幅降低（该问题可能是幻觉） |

加权的意义在于：如果 LLM 引用了一条不存在的法条来支撑某个违规判定，那么这条违规判定的可信度本身就打了折扣，对应的风险评分也应该降低。

#### 5.2.3 任务级别评分（overall_risk_score）

任务级别的总分是所有问题的加权分值之和：

```
overall_risk_score = Σ (issue_severity_score × citation_weight)
                   + Σ (missing_element_score)

封顶: 100 分
```

即：将该审查任务中发现的所有问题的分值（乘以各自的引用校验加权因子）相加，再加上缺失必备元素的分值，得到最终的任务总分。总分上限为 100。

#### 5.2.4 风险等级（risk_level）

风险等级由任务级别总分决定：

| 总分范围 | 风险等级 | 标识 | 含义 |
|----------|---------|------|------|
| 0 – 20 | `low`（低风险） | 🟢 绿色 | 可直接通过 |
| 21 – 50 | `medium`（中风险） | 🟡 黄色 | 建议人工复核 |
| 51 – 100 | `high`（高风险） | 🔴 红色 | 必须人工复核 |

#### 5.2.5 完整计算示例

假设某次审查发现以下问题：

| # | 问题 | severity | 基础分 | 引用状态 | 加权因子 | 加权后分值 |
|---|------|----------|--------|---------|---------|-----------|
| 1 | 暗示保本 | critical | 30 | verified | × 1.0 | **30** |
| 2 | 业绩数据缺少截止日期 | major | 20 | verified | × 1.0 | **20** |
| 3 | 诱导性推荐 | minor | 10 | corrected | × 0.8 | **8** |

另发现缺失 1 项 critical 必备元素（风险提示声明）：+25

```
overall_risk_score = 30 + 20 + 8 + 25 = 83
risk_level = high (83 > 50)
```

#### 报告结构说明

审查报告包含以下关键信息区块：

| 区块 | 内容 | 用途 |
|------|------|------|
| **头部信息** | 审查对象、产品、渠道、时间、风险评分 | 让复核人员一眼了解审查概况 |
| **问题汇总** | 违规问题数 + 缺失项数 | 快速判断工作量 |
| **违规明细** | 每条违规的位置、问题描述、法条引用（含校验状态）、修改建议 | 逐条复核的核心内容 |
| **缺失项** | 缺少的法定必备元素及对应法条 | 检查内容完整性 |
| **操作区** | 确认通过 / 确认违规 / 修改判定 / 添加备注 | 人工复核操作入口 |

每条法条引用后面的标记（✅已验证 / ⚠️引用已修正 / ❌未经验证）直接来自 `CitationVerifier` 的校验结果，让复核人员清楚地知道哪些引用可以信赖、哪些需要额外关注。
