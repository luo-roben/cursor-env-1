## 1. 法律法规采集

### 1.1 数据来源

| 来源分类 | 具体来源 | 采集方式 | 更新频率 |
|----------|----------|----------|----------|
| 国家法律 | 全国人大法规库、国家法律法规数据库 | 爬虫 + RSS | 实时监控 |
| 部门规章 | 证监会、银保监会、人民银行官网 | 爬虫 + API | 每日检查 |
| 行业自律 | 基金业协会、证券业协会 | 爬虫 | 每日检查 |
| 监管问答 | 证监会监管问答、窗口指导 | 人工导入 + 爬虫 | 发布即采集 |
| 处罚公告 | 各地证监局、央行分行 | 爬虫 | 每日检查 |
| 商业数据库 | 北大法宝、威科先行 | API 对接 | 按合同更新 |
| 内部制度 | 企业自有合规制度文档 | 人工上传 | 按需 |

### 1.2 采集流水线

```
┌──────────┐     ┌──────────┐     ┌──────────┐     ┌──────────┐
│ 源站监控  │ →   │ 增量抓取  │ →   │ 去重判断  │ →   │ 入库排队  │
│          │     │          │     │          │     │          │
│ 定时轮询  │     │ 全文提取  │     │ MD5 +    │     │ 标记状态: │
│ RSS订阅  │     │ 元数据    │     │ 标题相似度│     │ 待解析   │
│ Webhook  │     │ 抽取     │     │ 判重     │     │          │
└──────────┘     └──────────┘     └──────────┘     └──────────┘
```

**流水线各环节说明：**

1. **源站监控**：通过定时轮询（cron 调度）、RSS 订阅和 Webhook 回调三种方式监控法规源站更新。不同来源使用不同的监控策略——官方网站以定时轮询为主（每日 2-4 次），有 RSS 输出的源站优先使用 RSS，商业数据库通过 API 轮询或 Webhook 回调。
2. **增量抓取**：对监控到的新内容执行全文提取和元数据抽取。使用 HTTP 客户端获取页面内容，提取标题、发布机构、发布日期等元数据，并下载法规全文（HTML/PDF 均做纯文本转换）。
3. **去重判断**：计算法规全文的 MD5 哈希值，与已有法规库比对；同时使用标题文本相似度（阈值 > 0.9）进行模糊匹配，避免同一法规因标题微调而重复入库。
4. **入库排队**：通过去重的新法规存入 `law_sources` 表，状态标记为 `pending`（待解析），进入 LLM 解析流水线的输入队列。

### 1.3 法规来源元数据（LawSource）字段定义

每条采集的法规原文存储以下元数据，JSON 结构示例：

```json
{
  "source_id": "csrc-2024-001",
  "title": "公开募集证券投资基金销售机构监督管理办法",
  "issuer": "中国证监会",
  "issue_date": "2020-08-28",
  "effective_date": "2020-10-01",
  "doc_type": "部门规章",
  "status": "现行有效",
  "supersedes": ["csrc-2013-xxx"],
  "full_text": "...",
  "source_url": "http://www.csrc.gov.cn/...",
  "crawl_time": "2024-01-15T10:30:00Z",
  "parse_status": "pending"
}
```

**逐字段详细说明：**

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `source_id` | String | 是 | 全局唯一标识，格式: `{来源缩写}-{年份}-{序号}`，如 `csrc-2024-001`。来源缩写规则：`csrc`=证监会，`cbirc`=银保监会，`pboc`=人民银行，`amac`=基金业协会，`sac`=证券业协会，`npc`=全国人大。年份取发布年份，序号在同来源同年份下自增。 |
| `title` | String | 是 | 法规全称，如"公开募集证券投资基金销售机构监督管理办法"。必须使用官方发布的正式名称，不得使用简称或别名。 |
| `issuer` | String | 是 | 发布机构名称，如"中国证监会"、"中国人民银行"。使用机构官方全称。多机构联合发布时以逗号分隔，如"中国证监会,中国人民银行"。 |
| `issue_date` | Date | 是 | 发布日期，格式 `YYYY-MM-DD`。取法规正文中标注的"发布日期"或"印发日期"。 |
| `effective_date` | Date | 否 | 生效日期，格式 `YYYY-MM-DD`。部分法规发布即生效（此时为空，系统默认取 `issue_date`），部分法规明确注明生效日期（如"自2020年10月1日起施行"）。 |
| `doc_type` | Enum | 是 | 法规文件类型，枚举值：`法律` / `行政法规` / `部门规章` / `规范性文件` / `自律规则` / `监管问答`。层级效力从高到低排列，同一法条如涉及多层级冲突，以高层级为准。 |
| `status` | Enum | 是 | 法规当前状态，枚举值：`现行有效` / `已修改` / `已废止`。"已修改"表示该法规存在修正版本但原版仍部分有效；"已废止"表示已被新法规完全替代或明确废止。状态变更由新法规更新流程（见第 7 节）自动触发或人工标注。 |
| `supersedes` | String[] | 否 | 本法规替代的旧法规 `source_id` 列表。当新法规正文中明确提及"《xxx》同时废止"时填写。如 `["csrc-2013-xxx"]` 表示本法规替代了编号为 `csrc-2013-xxx` 的旧法规。被替代法规的 `status` 将被自动更新为 `已废止`。 |
| `full_text` | Text | 是 | 法规全文（纯文本格式）。从源站 HTML/PDF 中提取的纯文本内容，保留原始的章/节/条/款/项层级结构（以换行和缩进表示），去除 HTML 标签和格式噪声。长度无上限，典型值从数千字到数万字不等。 |
| `source_url` | String | 是 | 原始来源 URL，指向法规的官方发布页面。用于溯源审计和后续手动核对。人工上传的内部制度文档此字段填写内部文档管理系统的链接或文件路径。 |
| `crawl_time` | DateTime | 是 | 爬虫采集时间（UTC 时区），格式 `YYYY-MM-DDTHH:mm:ssZ`。标记数据进入系统的时间点，用于排查采集延迟和数据一致性问题。人工上传的法规取上传操作时间。 |
| `parse_status` | Enum | 是 | 解析状态流转，枚举值及含义：`pending`（待解析 — 刚入库，等待 LLM 解析流水线拾取）/ `parsing`（解析中 — LLM 正在处理）/ `parsed`（已解析 — LLM 解析完成，等待人工确认）/ `confirmed`（已确认 — 人工确认通过，知识已发布至检索库）/ `failed`（解析失败 — LLM 解析异常，需排查后重试）。状态机：`pending → parsing → parsed → confirmed`，`parsing → failed → pending`（重试）。 |

## 2. LLM 结构化解析引擎

### 2.1 四阶段解析流水线总览

```
法规原文 (LawSource, parse_status=pending)
    │
    ▼
┌─────────────────────────────────────────────────────────┐
│  阶段1: 法条拆分                                        │
│  法规全文 → LLM 按"条-款-项"拆分为独立法条单元            │
└────────────────────────┬────────────────────────────────┘
                         │
                         ▼
┌─────────────────────────────────────────────────────────┐
│  阶段2: 语义结构化                                       │
│  单条法条文本 → LLM 提取结构化信息 → 输出 JSON            │
└────────────────────────┬────────────────────────────────┘
                         │
                         ▼
┌─────────────────────────────────────────────────────────┐
│  阶段3: 向量化与索引                                     │
│  结构化知识 → Embedding 向量化 → 写入 Milvus              │
└────────────────────────┬────────────────────────────────┘
                         │
                         ▼
┌─────────────────────────────────────────────────────────┐
│  阶段4: 知识图谱构建                                     │
│  结构化知识 → 抽取实体与关系 → 写入 Neo4j                 │
└─────────────────────────────────────────────────────────┘
```

> **重要说明**：阶段 1 和阶段 2 依赖 LLM 执行（通过 Spring AI 的 ChatClient 调用），阶段 3 和阶段 4 是纯代码实现（调用 Embedding API + 数据库写入）。阶段 3 和阶段 4 在人工确认通过后自动触发。

### 2.2 阶段 1：法条拆分

```
┌─────────────────────────────────────────────────────────┐
│  阶段1: 法条拆分                                        │
│                                                         │
│  输入: 法规全文                                          │
│  处理: LLM 按"条-款-项"拆分为独立法条单元                 │
│  输出: 法条列表，每条保留完整上下文                        │
│                                                         │
│  Prompt 要点:                                           │
│  "请将以下法规文本按'条-款-项'结构拆分。                   │
│   每个最小单元保留其所属的条、款编号，                     │
│   以及适用于该单元的主语（如果主语在上文）。               │
│   保持原文不要改写。"                                    │
└─────────────────────────────────────────────────────────┘
```

**拆分规则：**
- 以"条"为基本单元，每条独立输出
- 如果一条中有多个"款"或"项"，且各款/项含有独立的规范语义，则拆分到款/项级别
- 定义类法条（如"本办法所称基金销售机构，是指……"）单独作为一个知识单元
- 保留上下文主语：如果某个款/项的主语在前文（如"基金销售机构及其从业人员从事基金销售业务，不得有下列情形：（一）……"），拆分后每项仍需携带完整主语

### 2.3 阶段 2：语义结构化

对阶段 1 拆分出的每条法条文本，调用 LLM 提取结构化信息，输出标准化 JSON。

#### 2.3.1 LLM 输出 JSON 字段定义

| 字段 | 类型 | 说明 | 是否LLM生成 | 是否可人工编辑 |
|------|------|------|------------|-------------|
| `source_ref.law_name` | String | 法律全称，如"公开募集证券投资基金销售机构监督管理办法"。对应法规来源元数据中的 `title` 字段。 | 是 | 是 |
| `source_ref.law_short_name` | String | 法律简称，用于 UI 显示和报告引用，如"基金销售管理办法"。LLM 根据法规名称自动生成常用简称。 | 是 | 是 |
| `source_ref.issuer` | String | 发布机构，如"中国证监会"。直接从法规来源元数据 `issuer` 字段复制而来，确保与采集源一致。 | 是 | 否（来自元数据） |
| `source_ref.article_id` | String | 法条编号，格式"第X条第Y款第Z项"，如"第24条第1款第1项"。严格按照法规原文中的编号体系生成，不可自行编造。 | 是 | 是 |
| `source_ref.original_text` | String | 法条原文，从法规全文中精确截取的法条文本，不可改写、不可摘要、不可增删。系统用此字段做溯源校验。 | 否（原文复制） | 否 |
| `structured.norm_type` | Enum | 规范类型，枚举值: `禁止` / `义务` / `权利` / `定义` / `程序`。`禁止`=不得做某事；`义务`=应当/必须做某事；`权利`=可以/有权做某事；`定义`=术语定义或范围界定；`程序`=流程性规定。 | 是 | 是 |
| `structured.subject` | String[] | 法条约束的主体列表。LLM 从法条中提取受约束的行为主体，如 `["基金销售机构", "从业人员"]`。一条法条可能约束多个主体。 | 是 | 是 |
| `structured.behavior` | String | 被禁止/要求的具体行为描述。对法条核心行为的精炼概括，如"以预期收益率、预计收益等方式宣传、介绍基金产品"。 | 是 | 是 |
| `structured.object` | String | 行为作用的对象，即行为施加于什么客体，如"基金产品"、"投资者"、"基金合同"。 | 是 | 是 |
| `structured.condition` | String | 适用前提条件，法条生效的限定性条件，如"从事基金销售业务时"、"在公开渠道发布宣传材料时"。如果法条无明确限定条件，此字段可为空。 | 是 | 是 |
| `structured.applicable_scenarios` | String[] | 适用业务场景列表。LLM 推断该法条在实际业务中可能适用的场景，如 `["基金销售", "基金宣传", "基金推介", "基金营销"]`。 | 是 | 是（可动态添加） |
| `structured.applicable_content_types` | String[] | 适用的内容形式列表。LLM 推断该法条可能适用于审查哪些类型的营销内容，如 `["营销海报", "宣传物料", "微信推文", "直播话术", "短视频脚本", "基金推介材料", "基金说明书", "路演PPT"]`。 | 是 | 是（可动态添加） |
| `structured.applicable_product_types` | String[] | 适用的产品类型列表。LLM 推断该法条适用的金融产品范围，如 `["公募基金", "ETF", "LOF", "指数基金", "混合基金", "股票基金", "债券基金", "货币基金"]`。 | 是 | 是（可动态添加） |
| `structured.key_phrases` | String[] | 法条中的关键词/短语。从法条原文中提取的核心用词，用于全文检索命中和关键词匹配，如 `["预期收益率", "预计收益", "宣传", "介绍"]`。 | 是 | 是 |
| `structured.semantic_extensions` | String[] | 语义延伸列表——法条未直接表述但隐含的违规变体。LLM 基于对法条语义的理解，推断出实际业务中可能出现的"打擦边球"的表述方式，如 `["暗示未来收益的具体数值", "使用历史收益暗示未来表现（不加免责声明）", "通过图表展示上升趋势暗示收益预期"]`。 | 是 | 是 |
| `structured.violation_examples` | String[] | 违规表述示例（3-5 个）——用于向量化后匹配待审查内容。LLM 生成的典型违规用语实例，使系统在审查时能通过语义相似度匹配到与这些示例类似的内容。如 `["这只基金预期年化收益12%", "预计明年能达到15%的回报"]`。 | 是 | 是（可添加） |
| `structured.compliant_examples` | String[] | 合规表述示例（1-3 个）——帮助 LLM 区分合规与违规的边界。提供正确的表述方式作为对照，使审查时 LLM 能精确判断边界案例。如 `["该基金过去三年年化收益率为8.5%（截至2024年12月31日，过往业绩不代表未来表现）"]`。 | 是 | 是（可添加） |
| `structured.penalty` | String | 违反后果/罚则。引用法规中对应的罚则条款，如"参照第49条，责令改正，给予警告，并处三万元以下罚款"。如果法条本身未规定罚则，LLM 应尝试关联同部法规中的总则/罚则章节。 | 是 | 是 |
| `structured.related_articles` | String[] | 关联法条编号列表。与当前法条在语义或法律效力上相关的其他法条，如 `["第24条第1款第2项", "第25条", "广告法第4条"]`。关联关系包括：同条其他款项、引用关系、补充关系、上位法/下位法关系等。 | 是 | 是 |

#### 2.3.2 `applicable_*` 字段的动态特性说明

`applicable_scenarios`、`applicable_content_types`、`applicable_product_types` 这三组字段具备以下重要特性：

1. **存储方式**：在 PostgreSQL 中以 `JSONB` 数组类型存储，天然支持动态增删元素，**无需变更数据库 Schema，无需修改代码**。

2. **LLM 初始生成**：当 LLM 首次解析法条时，会根据对法条语义的理解做出"最佳猜测"（best guess），尽可能覆盖常见的适用场景、内容类型和产品类型。但 LLM 不可能穷举所有情况。

3. **人工确认阶段精炼**：在人工确认工作台（见第 5 节）中，合规专家可以：
   - 删除 LLM 误添加的不适用项
   - 添加 LLM 遗漏的适用项
   - 调整措辞使其更精确

4. **运行时动态管理**：知识发布后，这些字段仍可通过以下方式随时修改：
   - **人工确认工作台**：合规团队重新编辑已发布的知识条目
   - **管理 API**：通过 RESTful API 批量添加/移除标签，便于系统集成
   - 修改后知识条目自动重新索引（向量化更新）

5. **新类型自动可用**：当系统中新增了一种内容类型（如"短视频字幕"）或产品类型（如"REITs"），该新类型立即可用于所有法条的 `applicable_*` 字段标注，无需任何代码发布。

### 2.4 阶段 3：向量化与索引

> **本阶段是纯代码实现，不涉及 LLM 推理。** 它是自动化流水线的一部分，在人工确认发布后自动触发执行。

#### 2.4.1 技术方案

- **Embedding 模型**：`bge-large-zh-v1.5`（中文语义向量化模型，1024 维）
- **调用方式**：通过 Spring AI 的 `EmbeddingClient` 接口调用 Embedding 模型 API
- **向量存储**：Milvus 向量数据库，按法规来源分 Partition
- **触发时机**：人工确认工作台点击"确认发布"后，系统自动异步执行向量化

#### 2.4.2 多粒度 Embedding 策略

对每条确认发布的法条知识，生成 4 种粒度的 Embedding 向量：

| 向量类型 | 向量化文本来源 | 用途 |
|---------|--------------|------|
| 法条原文 Embedding | `source_ref.original_text` | 用于精确法条检索 |
| 行为描述 Embedding | `structured.behavior` + `structured.condition` | 用于审查时语义匹配 |
| 违规示例 Embedding | `structured.violation_examples` 中每条示例 | 用于与待审查内容匹配 |
| 语义延伸 Embedding | `structured.semantic_extensions` 中每条延伸 | 用于捕捉变体表述 |

#### 2.4.3 实现伪代码

```java
/**
 * 法条知识向量化服务
 * 在人工确认发布后自动触发
 */
@Service
public class ArticleVectorizationService {

    private final EmbeddingClient embeddingClient;       // Spring AI Embedding 客户端
    private final MilvusServiceClient milvusClient;      // Milvus Java SDK 客户端

    private static final String COLLECTION_NAME = "law_knowledge_vectors";

    /**
     * 对单条法条知识执行多粒度向量化并写入 Milvus
     * @param article 已确认的法条知识对象
     */
    public void vectorizeAndIndex(LawArticle article) {

        // --- 1. 法条原文 Embedding ---
        float[] originalTextVector = embeddingClient
            .embed(article.getOriginalText())   // 调用 bge-large-zh-v1.5 API
            .getOutput();                        // 返回 float[1024]

        insertToMilvus(article.getId(), "original_text",
                       originalTextVector, article.getSourceId());

        // --- 2. 行为描述 Embedding ---
        String behaviorText = article.getBehavior() + " " + article.getCondition();
        float[] behaviorVector = embeddingClient
            .embed(behaviorText)
            .getOutput();

        insertToMilvus(article.getId(), "behavior",
                       behaviorVector, article.getSourceId());

        // --- 3. 违规示例 Embedding（每条示例独立向量化） ---
        for (String example : article.getViolationExamples()) {
            float[] exampleVector = embeddingClient
                .embed(example)
                .getOutput();

            insertToMilvus(article.getId(), "violation_example",
                           exampleVector, article.getSourceId());
        }

        // --- 4. 语义延伸 Embedding（每条延伸独立向量化） ---
        for (String extension : article.getSemanticExtensions()) {
            float[] extensionVector = embeddingClient
                .embed(extension)
                .getOutput();

            insertToMilvus(article.getId(), "semantic_extension",
                           extensionVector, article.getSourceId());
        }
    }

    /**
     * 将单条向量插入 Milvus
     */
    private void insertToMilvus(Long articleId, String vectorType,
                                float[] vector, String sourceId) {

        List<InsertParam.Field> fields = List.of(
            new InsertParam.Field("article_id",   List.of(articleId)),
            new InsertParam.Field("vector_type",   List.of(vectorType)),
            new InsertParam.Field("embedding",     List.of(vector)),
            new InsertParam.Field("status",        List.of("published"))
        );

        InsertParam insertParam = InsertParam.newBuilder()
            .withCollectionName(COLLECTION_NAME)
            .withPartitionName(sourceId)          // 按法规来源分 Partition
            .withFields(fields)
            .build();

        milvusClient.insert(insertParam);
    }
}
```

#### 2.4.4 Milvus Collection Schema

```
Collection: law_knowledge_vectors
├── article_id       : Int64   (法条知识 ID)
├── vector_type      : VarChar (向量类型: original_text / behavior / violation_example / semantic_extension)
├── embedding        : FloatVector(1024)  (bge-large-zh-v1.5 输出的 1024 维向量)
├── status           : VarChar (published / deprecated)
└── Partition Key    : source_id (按法规来源分区)

Index: IVF_FLAT on embedding, nlist=1024
Metric: COSINE (余弦相似度)
```

### 2.5 阶段 4：知识图谱构建

基于阶段 2 的结构化 JSON 输出，将法条知识中的实体和关系写入 Neo4j 知识图谱。

#### 2.5.1 实体定义

| 实体类型 | 标签 (Label) | 核心属性 | 说明 |
|---------|-------------|---------|------|
| 法律 | `Law` | `name`, `short_name`, `issuer`, `doc_type`, `status` | 一部完整的法律/法规 |
| 法条 | `Article` | `article_id`, `original_text`, `norm_type`, `behavior`, `penalty` | 一条具体的法律条文 |
| 规范主体 | `Subject` | `name` | 法条约束的行为主体，如"基金销售机构" |
| 规范行为 | `Behavior` | `description`, `norm_type` | 被禁止/要求的具体行为 |
| 产品类型 | `ProductType` | `name` | 金融产品类型，如"公募基金" |
| 内容类型 | `ContentType` | `name` | 营销内容形式，如"营销海报" |

#### 2.5.2 关系定义

| 关系类型 | 起始实体 | 终止实体 | 说明 | 示例 |
|---------|---------|---------|------|------|
| `CONTAINS` | Law | Article | 法律包含法条 | 《基金销售管理办法》-[CONTAINS]->第24条 |
| `CONSTRAINS` | Article | Subject | 法条约束主体 | 第24条-[CONSTRAINS]->基金销售机构 |
| `PROHIBITS` | Article | Behavior | 法条禁止行为（norm_type=禁止） | 第24条-[PROHIBITS]->以预期收益率宣传 |
| `REQUIRES` | Article | Behavior | 法条要求行为（norm_type=义务） | 第25条-[REQUIRES]->标注数据来源 |
| `APPLIES_TO` | Article | ProductType | 法条适用于产品类型 | 第24条-[APPLIES_TO]->公募基金 |
| `APPLIES_TO` | Article | ContentType | 法条适用于内容类型 | 第24条-[APPLIES_TO]->营销海报 |
| `REFERENCES` | Article | Article | 法条间交叉引用 | 第24条-[REFERENCES]->广告法第4条 |
| `SUPERSEDED_BY` | Article | Article | 新旧法条替代关系 | 旧法第X条-[SUPERSEDED_BY]->新法第Y条 |

#### 2.5.3 知识图谱应用场景

- **法条关联查询**：给定一条法条，查询所有关联法条（通过 `REFERENCES` 和 `SUPERSEDED_BY` 关系的多跳遍历）
- **主体维度检索**：查询某一主体（如"基金销售机构"）受到哪些法条的约束
- **影响分析**：当一部法律修订时，通过知识图谱快速识别所有受影响的法条和关联法条
- **冲突检测**：检测不同法规的法条之间是否存在矛盾或冲突

## 3. LLM 调用方式详解

本节详细说明知识构建层中 LLM 的调用方式、技术实现和工程策略。

### 3.1 调用架构

```
┌──────────────────────────────────────────────────────────────┐
│  知识构建层 LLM 调用架构                                       │
│                                                               │
│  ┌─────────────┐     ┌──────────────┐     ┌──────────────┐  │
│  │ 解析任务队列  │ →   │ Spring AI    │ →   │ LLM API      │  │
│  │ (RabbitMQ)  │     │ ChatClient   │     │ (DeepSeek /  │  │
│  │             │     │              │     │  通义千问)    │  │
│  │ 异步消费    │     │ 直接 API 调用 │     │              │  │
│  │ 批量处理    │     │ 非流式输出    │     │ 可容忍高延迟  │  │
│  └─────────────┘     └──────────────┘     └──────────────┘  │
│                              │                                │
│                              ▼                                │
│                       ┌──────────────┐                       │
│                       │ Structured   │                       │
│                       │ Output 解析  │                       │
│                       │              │                       │
│                       │ JSON → Java  │                       │
│                       │ Object 映射  │                       │
│                       └──────────────┘                       │
└──────────────────────────────────────────────────────────────┘
```

**核心要点：**

1. **调用方式**：通过 Spring AI 的 `ChatClient` 进行**直接 API 调用**（HTTP REST），不涉及模型微调（fine-tuning）。这是标准的 prompt engineering + structured output 模式。

2. **异步/批量处理**：知识构建层的 LLM 调用是**离线批量任务**，不是实时在线请求。法规解析任务通过消息队列（RabbitMQ）异步消费，可以容忍较高的延迟（单次调用 10-30 秒均可接受）。

3. **非流式输出**：与审查执行层不同，知识构建层不需要流式返回（streaming），因为没有用户在等待实时结果。使用非流式调用以获取完整的 JSON 响应。

### 3.2 Prompt 设计

知识构建层的 Prompt 由两部分组成：

**System Instruction（系统指令）：**

```
你是一名资深的中国金融法律法规解析专家。你的任务是将法律条文解析为结构化 JSON。

解析规则：
1. 严格基于法条原文提取信息，不编造、不推测法律未规定的内容
2. original_text 字段必须是法条原文的精确复制，不可改写
3. norm_type 只能是以下枚举值之一：禁止/义务/权利/定义/程序
4. violation_examples 生成 3-5 个在实际营销场景中可能出现的违规表述
5. compliant_examples 生成 1-3 个正确的合规表述作为对照
6. semantic_extensions 重点关注"打擦边球"的变体表述
7. applicable_* 字段尽可能覆盖所有适用场景，宁多勿少（后续由人工精炼）

请严格按照指定的 JSON Schema 输出。
```

**User Message（用户消息）：**

```
请解析以下法条：

法律名称：{law_name}
发布机构：{issuer}
法条编号：{article_id}
法条原文：
{original_text}
```

### 3.3 结构化输出解析

使用 Spring AI 的 **Structured Output** 特性，将 LLM 返回的 JSON 文本自动映射为 Java 对象：

```java
// 使用 Spring AI 的 BeanOutputConverter 实现结构化输出
BeanOutputConverter<ArticleKnowledge> outputConverter =
    new BeanOutputConverter<>(ArticleKnowledge.class);

String response = chatClient.prompt()
    .system(systemInstruction)
    .user(userMessage)
    .call()
    .content();

// 自动将 JSON 字符串解析为 Java 对象
ArticleKnowledge knowledge = outputConverter.convert(response);
```

Spring AI 的 Structured Output 机制会：
1. 根据 Java 类的字段定义自动生成 JSON Schema
2. 将 JSON Schema 附加到 Prompt 中，指导 LLM 按指定格式输出
3. 调用后自动解析 JSON 响应并映射到 Java 对象

### 3.4 重试与错误处理

```
┌──────────────────────────────────────────────────────────┐
│  LLM 调用错误处理流程                                      │
│                                                           │
│  调用 LLM API                                             │
│      │                                                    │
│      ├── 成功 + JSON 格式正确 → 解析为 Java 对象 → 入库    │
│      │                                                    │

│      │      │   "上一次的输出格式有误，请严格按 JSON        │

│      │      │                                             │
│      │      ├── 重试 2: 简化 Prompt + 强调格式             │

│      │            如果 DeepSeek 持续格式错误，              │

│      │                                                    │
│      │      3 次重试均失败 → parse_status = failed         │
│      │      → 进入人工排查队列                             │
│      │                                                    │
│      ├── API 调用失败（网络/超时/限流）                    │
│      │      → 指数退避重试（1s → 2s → 4s），最多 5 次     │
│      │      → 仍失败则任务重新入队，延迟 5 分钟后重试       │
│      │                                                    │
│      └── API 返回内容安全拒绝                              │
│            → 记录日志，parse_status = failed               │
│            → 标记为需人工处理                               │
└──────────────────────────────────────────────────────────┘
```

### 3.5 模型选择策略

| 考量维度 | 说明 |
|---------|------|
| **推荐模型** | DeepSeek、通义千问等**性价比较高**的模型 |
| **选择理由** | 知识构建层的 LLM 输出**会经过人工确认**环节（见第 5 节），因此不需要最高精度的模型。使用价格较低的模型可大幅降低批量解析数千条法条的成本。 |
| **精度保障** | LLM 输出只是"初稿"，合规专家在人工确认工作台中审核修正，最终质量由人工兜底。 |
| **备用模型** | 当主模型输出质量持续不佳（JSON 格式错误率 > 10%）时，自动切换到更强的模型（如 GPT-4o、Claude）。 |
| **成本估算** | 以 DeepSeek 为例，解析 3,500 条法条，平均每条输入 ~500 tokens + 输出 ~800 tokens ≈ 4.5M tokens 总消耗，成本约数十元人民币。 |

**工作台功能说明：**

- **右侧面板**：展示 LLM 解析结果的每个字段，每个字段旁带 `[✓]`（确认）复选框
- **违规示例 / 语义延伸 / 合规示例**：支持逐条确认/删除，并可通过 `[+ 添加]` 按钮新增
- **`applicable_*` 字段**：以多选标签（tag）形式展示，可点击删除或添加新标签
- **顶部统计栏**：实时显示待确认、已确认、退回数量

### 5.2 确认操作与系统行为

| 操作 | 系统行为 |
|------|----------|
| **✅ 确认发布** | 知识条目状态变为 `published`，自动触发**阶段 3（向量化与索引）**和**阶段 4（知识图谱构建）**，法条进入向量库索引，可被审查执行层检索到。法规来源的 `parse_status` 在所有法条均确认后更新为 `confirmed`。 |
| **📝 修改后发布** | 人工修改内容覆盖 LLM 解析结果（如调整违规示例、修正 `norm_type`、增删 `applicable_*` 标签等），修改内容保存后执行与"确认发布"相同的后续流程。同时记录修改日志（原始值 → 修改值、修改人、修改时间），用于后续分析 LLM 解析质量。 |
| **↩️ 退回重新解析** | 附带修改意见（如"主体识别错误"、"行为描述不准确"），系统将修改意见拼入 Prompt，用修正后的 Prompt 重新调用 LLM 解析该法条。退回次数上限为 3 次，超过后转入人工手动编辑模式。 |

## 7. 新法规自动更新流程

```
新法规发布（监控到源站更新）
        │
        ▼
  ┌───────────┐
  │ 自动采集   │ ← 爬虫定时轮询 + RSS 订阅
  └─────┬─────┘
        │
        ▼
  ┌───────────┐
  │ 去重判断   │ ← MD5 + 标题相似度 > 0.9 判为已有
  └─────┬─────┘
        │ (新法规)
        ▼
  ┌───────────┐
  │ LLM 解析  │ ← 复用第 2 节的四阶段解析流水线
  └─────┬─────┘
        │
        ▼
  ┌───────────┐
  │ 自动关联   │ ← 检测是否替代了旧法规（如"本办法自发布之日起施行，
  │ 新旧法规   │    《xxx暂行办法》同时废止"）
  └─────┬─────┘   → 旧法条标记为 superseded, 新法条标记 supersedes
        │
        ▼
  ┌───────────────┐
  │ 推送人工确认   │ ← 通知合规团队: "系统检测到新法规发布, 已完成自动解析,
  │ (5.1 工作台)  │    请确认后发布"
  └───────┬───────┘
          │
          ▼ (确认发布)
  ┌───────────────┐
  │ 更新知识库     │ ← 新法条向量入库, 知识图谱更新关系
  │ + 失效旧知识   │ ← 被替代的旧法条标记 deprecated，从检索优先级中降权
  └───────────────┘
```

**更新流程关键环节说明：**

1. **自动关联新旧法规**：LLM 分析新法规正文中的"废止条款"（通常在附则中），自动提取被废止法规的名称，与系统中已有法规做匹配。匹配成功后建立 `SUPERSEDED_BY` 关系。

2. **旧知识降权而非删除**：被替代的旧法条不从向量库中物理删除，而是标记为 `deprecated`。在检索时 `deprecated` 法条的权重降至 0.1（几乎不会被检索到），但在知识图谱中仍保留历史关系链路，供溯源和审计使用。

3. **通知机制**：新法规自动解析完成后，通过系统内消息 + 邮件通知合规团队。通知内容包括：新法规名称、解析出的法条数量、检测到的被替代旧法规列表、待确认链接。

4. **部分更新场景**：如果新法规是对旧法规的"修改"而非"替代"（如"关于修改《xxx》的决定"），则只对修改涉及的具体条款执行更新，未修改的条款保持不变。
