# 智能合规审查系统 — 总览

> 版本: v2.0 | 架构范式: LLM + RAG + ACE (Agentic Context Engineering)

---

## 一、系统定位与核心理念

### 1.1 一句话定位

**用 LLM 代替人工阅读法律法规，用 RAG 检索代替手动规则路由，用案例沉淀代替规则维护，构建一个"越用越准"的智能合规审查引擎。**

### 1.2 核心设计原则

| 序号 | 原则 | 说明 |
|------|------|------|
| P1 | **机器读法律，人只做确认** | 法律法规由 LLM 自动解析为结构化知识，人工只做 review & approve |
| P2 | **语义检索，不靠标签** | 审查时按内容语义从知识库检索相关法条，不维护"内容类型→规则集"的手动映射 |
| P3 | **每次审查动态组装上下文** | ACE 架构：根据当前审查的内容类型、产品类型、渠道，实时检索法条+案例组装 prompt |
| P4 | **越用越准** | 每次人工复核的结果沉淀为新案例，持续增强知识库 |
| P5 | **可溯源** | 每条审查结论必须附上法条原文引用，可追溯、可审计 |
| P6 | **简单自定义** | 企业用自然语言描述要求，不写规则、不选标签、不配引擎 |

## 二、新旧方案对比

### 2.1 传统方案 vs 本系统方案

```
❌ 传统方案（Drools/正则驱动）:
法律法规文本 → 人工阅读 → 人工总结规则 → 人工写 DRL/正则 → 人工维护标签映射
                ↑ 几百部法律、几千条法条，人工根本写不完，也维护不了

✅ 本系统方案（LLM + RAG 驱动）:
法律法规文本 → LLM 自动解析 → 结构化知识入库 → 审查时 LLM 基于检索到的知识做判断
                ↑ 机器读法律，人只做最终确认；知识库自动扩展，无需手动维护
```

### 2.2 关键差异

| 维度 | 传统方案（Drools/正则） | 本系统方案（LLM + RAG） |
|------|------------------------|------------------------|
| 法规解读 | 人工阅读，人工总结规则 | LLM 自动解析为结构化知识，人工仅做确认 |
| 规则维护 | 手动编写 DRL / 正则表达式 | 无需手动规则，知识库自动扩展 |
| 内容路由 | 人工维护"内容类型→规则集"映射表 | 按内容语义自动检索匹配法条（向量 + 结构化混合检索） |
| 新法规响应 | 人工阅读 → 人工编写规则，周期长 | LLM 自动解析 → 人工确认即上线，周期短 |
| 边界 case 处理 | 正则无法处理语义变体 | LLM 原生理解语义，案例沉淀持续改进 |
| 企业自定义 | 需要技术人员配置规则引擎 | 自然语言描述需求，零技术门槛 |

### 3.1 第一层：知识构建层（离线/准实时）

**目标：让机器读懂法律。**

- **法规采集**：通过爬虫、RSS 订阅、人工导入等方式，持续采集国家法律、部门规章、行业自律规则、监管问答、处罚公告等法规原文。
- **LLM 结构化解析**：将法规原文送入 LLM，按"条-款-项"拆分并提取结构化信息（规范类型、适用场景、违规示例、语义延伸等），生成结构化知识条目。
- **人工确认**：LLM 解析结果不直接入库，需经人工确认工作台审核后发布。
- **多模态存储**：结构化数据存 PostgreSQL，向量存 Milvus，知识图谱存 Neo4j，全文索引存 Elasticsearch。
- **历史案例导入**：企业历史审核案例经结构化标注后入库，作为后续审查的参考依据。

详见：[01-knowledge-layer.md](01-knowledge-layer.md)、[02-case-management.md](02-case-management.md)

### 3.2 第二层：审查执行层（在线）

**目标：每次审查动态组装最优上下文。**

- **快速过滤**：LLM 前的轻量级预处理（禁用词匹配 + 必备声明检查），耗时 < 10ms。
- **内容解析**：按内容类型（图片/PDF/文本/视频等）选择对应解析器，统一输出分段文本。
- **ACE 上下文动态组装**（核心）：五路并行检索——按内容类型、按产品类型、按内容语义（向量检索）、按历史案例（向量检索）、加载企业自定义规则——合并去重后组装为最终 prompt。
- **LLM 调用**：将组装好的上下文 + 待审查内容送入 LLM，获取结构化审查结果。
- **后处理**：法条引用校验（防幻觉）、风险评分计算、审查报告生成。

详见：[03-review-engine.md](03-review-engine.md)、[04-content-routing.md](04-content-routing.md)

### 3.3 第三层：进化学习层（持续）

**目标：越用越准。**

- **人工复核**：审查结果进入复核队列，复核人可确认、驳回、修改或补充 LLM 的判定。
- **案例沉淀**：每次人工复核自动生成案例条目，计算学习价值分，向量化后入库。
- **知识库增强**：新沉淀的案例可被后续审查检索，形成"审查 → 复核 → 案例 → 更好的审查"正循环。
- **新法规更新**：监控法规源站，自动采集新法规并触发 LLM 解析 → 人工确认 → 知识库更新。
- **系统进化监控**：跟踪 AI 准确率、误判率、漏检率等指标，低准确率维度自动触发法条复核。

详见：[05-feedback-loop.md](05-feedback-loop.md)

## 五、常见技术问题

### Q1: 这个系统是直接调用 LLM API 的吗？

**是的，系统通过 Spring AI 框架直接调用 LLM API。** 不涉及任何模型微调（fine-tuning）或训练，LLM 的行为完全通过 prompt engineering + 检索到的上下文（RAG 模式）来控制。

系统中有两个位置调用 LLM：

| 调用位置 | 层级 | 特点 | 用途 |
|----------|------|------|------|
| **知识构建层**（离线） | 第一层 | 批量处理，不要求实时性 | 将法律法规原文解析为结构化知识条目 |
| **审查执行层**（在线） | 第二层 | 实时调用，对延迟敏感 | 基于检索到的法条 + 案例上下文，对待审查内容进行合规判定 |

两个位置都是通过 Spring AI 的 `ChatClient` 发起直接 API 调用。`ChatClient` 是 Spring AI 对各种 LLM 提供商（GPT-4o、Claude、DeepSeek、通义千问等）的统一抽象封装，底层是标准的 HTTP 请求。它提供以下能力：

- **统一接口**：屏蔽不同 LLM 厂商的 API 差异，代码层面通过配置切换模型
- **自动重试**：内置 HTTP 调用的重试机制（如遇到 429 Rate Limit 或 5xx 错误）
- **限流控制**：配合 Spring AI 的 rate limiting 机制，控制并发调用量
- **结构化输出解析**：支持将 LLM 返回的 JSON 文本自动反序列化为 Java 对象（`BeanOutputConverter`），无需手动 parse

**重点强调：系统不训练、不微调任何模型。** 所有的"智能"来自两方面的组合：(1) prompt 中精心设计的指令，(2) RAG 检索到的相关法条知识和历史案例。模型本身是通用模型，通过上下文注入领域知识。

### Q2: applicable_scenarios、applicable_content_types 等字段是可以动态添加调整的吗？

**是的，这些字段完全动态，无需修改任何代码。**

这些字段在 PostgreSQL 中以 **JSONB 数组**类型存储（如 `applicable_content_types JSONB`），本质上是一个灵活的字符串列表，不是枚举或固定值。

有三种方式可以添加或修改这些字段的值：

**方式一：LLM 自动生成**

当 LLM 解析一条新的法律条文时，它会根据法条内容自动推断该法条适用的场景、内容类型和产品类型，并填充到对应字段中。例如 LLM 解析出某法条适用于 `["营销海报", "微信推文", "直播话术", "短视频脚本"]`，这些值由 LLM 根据语义理解自动生成，不受预定义列表限制。

**方式二：人工确认时调整**

在人工确认工作台中，复核人员可以对 LLM 生成的列表进行增删改操作。例如：
- 添加 LLM 遗漏的内容类型（如"小红书笔记"）
- 删除不适用的场景
- 修正产品类型的描述

**方式三：管理 API 批量更新**

系统管理员可以通过管理 API 对已有的法条知识条目进行批量更新，例如当业务新增了一种内容类型"抖音直播"时，可以将所有相关法条的 `applicable_content_types` 批量追加该值。

**为什么"不用改代码"？**

审查执行层在检索法条时，使用的是动态的结构化查询：

```sql
SELECT * FROM law_articles
WHERE 'content_type' = ANY(applicable_content_types)
AND status = 'published'
```

这里的 `applicable_content_types` 是 JSONB 数组，`ANY` 操作符会动态匹配数组中的任意元素。当你在某条法条的 `applicable_content_types` 中增加了 `"抖音直播"`，下次有"抖音直播"类型的内容提交审查时，该法条就会被自动检索到。无需修改代码、无需重启服务、无需重新部署。

### Q3: 向量化与索引（阶段3）需要代码实现吗？

**需要，这是知识构建流水线中的关键代码环节。**

具体需要实现以下组件：

**1. Embedding 服务**

接收文本输入，调用 Embedding 模型（如 `bge-large-zh-v1.5`）生成向量表示。使用 Spring AI 的 `EmbeddingClient` 封装模型调用：

```java
// 实际代码流程（伪代码）
String text = article.getOriginalText();
float[] vector = embeddingClient.embed(text);  // 调用 Embedding 模型 API
milvusClient.insert("law_knowledge_vectors", vector, metadata);
```

**2. Milvus 客户端**

将生成的向量插入 Milvus 向量数据库，并附带结构化元数据（法条 ID、法规名称、状态等），用于后续的过滤检索。

**3. 流水线编排器**

在 LLM 解析 + 人工确认 完成后，自动触发向量化流程。这是一个事件驱动的流程：

```
人工确认发布 → 触发事件 → 向量化服务
    → 对法条原文生成 Embedding
    → 对行为描述生成 Embedding
    → 对违规示例（每条）生成 Embedding
    → 对语义延伸（每条）生成 Embedding
    → 批量写入 Milvus
```

**这不是一个手动步骤**——整个流程是自动化的，作为 Spring Boot 服务的一部分运行在知识构建流水线中。人工确认发布后，系统自动完成向量化和索引，无需人工干预。

Spring AI 的 `EmbeddingClient` 封装了底层的 HTTP 调用（向 Embedding 模型服务发送请求），开发者只需关注文本输入和向量输出。

### Q4: 向量语义检索真的准确吗？（"收益率20%"能准确命中第24条？）

**单纯的向量检索确实有局限性，但本系统采用的是混合检索策略（Hybrid Retrieval），大幅提高了检索准确率。**

系统的检索由三条路径组合而成：

| 检索路径 | 擅长场景 | 示例 |
|----------|----------|------|
| **向量语义检索**（Milvus） | 捕捉语义相似性，处理变体表述 | "亏损概率很小" → 命中"保本承诺"相关法条 |
| **结构化字段查询**（PostgreSQL） | 精确匹配内容类型、产品类型 | `content_type = '营销海报'` → 命中海报相关的格式/完整性法条 |
| **关键词/BM25 检索**（Elasticsearch） | 捕捉精确术语 | "预期收益率" → 精确命中包含该关键词的法条 |

**三条路径的结果通过 Reciprocal Rank Fusion（RRF）算法合并。** RRF 的核心思想是：如果一个法条在多条检索路径中都排名靠前，它在最终合并结果中的排名就更高。计算公式：

```
RRF_score(d) = Σ 1 / (k + rank_i(d))
```

其中 `k` 是常数（通常取 60），`rank_i(d)` 是文档 `d` 在第 `i` 条检索路径中的排名。

**为什么"收益率20%"能准确命中第24条？**

1. **关键词路径**：Elasticsearch 中的 BM25 检索会精确匹配到"预期收益率"这个关键词，命中第24条。
2. **向量路径**：法条知识中预生成了 `violation_examples`（如"有望获得20%以上收益"）和 `semantic_extensions`（如"暗示未来收益的具体数值"），这些文本也做了向量化。因此向量空间中已经包含"收益率20%"这样的违规示例，语义匹配非常精确。
3. **结构化路径**：如果已知内容类型是"营销海报"、产品类型是"公募基金"，结构化查询会精确命中所有适用的法条，进一步缩小范围。

**准确率随时间持续提升：** 每次人工复核产生的新案例（例如："近一年收益率28%" → 违规）都会被向量化入库。下次有类似表述（如"收益率20%"）提交审查时，向量检索不仅能命中法条本身，还能命中这些高度相似的真实案例。这就是"越用越准"闭环在检索层面的体现。

### Q5: 风险评分是评整个审查任务还是单个审查点？

**两个层级都有评分，分别对应不同用途。**

**层级一：Issue 级评分（单个审查点）**

每个在具体文本段落中发现的问题都有独立的严重等级（severity），对应不同的分值：

| 严重等级 | 分值 | 示例 |
|----------|------|------|
| critical（严重违规） | +30 | 保本承诺、虚假宣传 |
| major（重要违规） | +20 | 业绩数据缺少截止日期/来源 |
| minor（轻微违规） | +10 | 措辞不够严谨 |
| info（建议） | +5 | 表述可优化但不构成违规 |

此外，每个 issue 的分值还会根据法条引用的校验状态加权：
- `verified`（已验证）：× 1.0
- `corrected`（已修正）：× 0.8
- `unverified`（未验证）：× 0.5

**层级二：Task 级评分（整个审查任务）**

审查任务的整体 `risk_score`（0-100）是所有段落中所有 issue 分值的加权求和，封顶 100 分。同时，缺失必备元素也会计入：
- 缺失 critical 必备元素：+25
- 缺失 recommended 必备元素：+10

Task 级评分决定了整体风险等级（`risk_level`），并直接驱动人工复核的优先级：

| 风险评分 | 风险等级 | 复核策略 |
|----------|----------|----------|
| 0-20 | 低风险（low） | 抽样复核（10%） |
| 21-50 | 中风险（medium） | 部分复核（50%） |
| 51-100 | 高风险（high） | 必须人工复核（100%） |

**总结：issue 级评分给出每个问题的精确定位和严重程度，task 级评分汇总为整体风险判断，二者共同服务于人工复核的优先级排序。**

### Q6: 案例的 reviewed_content 存给模型会不会特别长？

**不会，因为案例存储的是分段（segment）文本，不是完整文档。**

一条案例的 `reviewed_content` 是被审查内容中的一个段落/片段，通常只有 10-100 个字符。例如：

- `"亏损概率很小"`（7个字）
- `"近一年收益率28%，排名前10%"`（15个字）
- `"现在买入，亏损概率很小，值得关注"`（16个字）

当案例被检索后作为 LLM 上下文时，每条案例会被压缩为简短格式：

```
案例#12345: "亏损概率很小" → 违规(保本暗示) | 法条:第24条第1款第2项
```

**Token 消耗估算：**

| 项目 | 数值 |
|------|------|
| 单条案例压缩后长度 | 约 50-80 tokens |
| 每次检索案例数（top_k） | 约 10 条 |
| 案例上下文总 token 量 | 约 500-800 tokens |
| 系统总 token 预算中案例部分 | 最多 ~3,000 tokens |

对比 LLM 的上下文窗口（GPT-4o 为 128K tokens，Claude 为 200K tokens），500-800 tokens 的案例上下文远在预算之内。

即使在极端情况下（检索到 30 条高度相关案例），token 消耗也仅约 1,500-2,400 tokens，仍然可控。上下文组装器（ContextAssembler）会按相关度得分排序，当总 token 超出预算时，从低相关度的案例开始裁剪。

**为什么不存完整文档？** 因为审查的粒度本身就是分段的——LLM 对每个段落独立做合规判定，人工复核也是逐条确认/驳回。案例自然以段落为单位存储，既精确（一个段落对应一个判定）又高效（token 开销小）。
